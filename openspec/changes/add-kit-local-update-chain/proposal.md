# Proposal

## Why

当前 Kit 已能串联打包和上传发布，Windows 桌面更新中心也能独立下载安装，但缺少把同一发布交给本机更新并在重启后核实结果的 Kit 能力。用户需要一条可重复使用的流程，而不是每次发布后手动切换更新中心，也不能把安装器启动或退出误判为整条流程成功。

## What Changes

- 增加受控的 Kit 本机更新能力，复用更新中心和独立桌面更新助手，不通过任意 RPC、复制安装命令或结束同名进程绕过管理入口。
- 提供“打包 → 发布 → 本机更新”的组合生成／保存路径，复用当前 Session 内用户选择的真实构建 Kit；依次执行，前一步失败不进入后续步骤。
- 更新只消费本次链路已成功发布的冻结制品身份：版本、buildId、通道、制品 ID、大小、摘要及不可变清单；不再次按浮动 latest 猜测安装对象。
- 发布保留既有确认机制；本机安装另行展示冻结计划并由 Kit 面板明确确认。现有发布代确认不自动扩张为安装和重启授权。
- 在安装交接前持久化运行归属与验收凭据；独立助手接管后，重启自动核对同一运行的安装回执和实际桌面／Backend 版本，未确认不得报成功或自动重装。
- 展示预检、下载校验、等待确认、安装交接、等待重连、验收成功／失败／未知，并防止更新覆盖其他更新任务或中断仍在运行的业务任务。

## Capabilities

### New Capabilities

- `kit-local-update-chain`：当前 Session 执行节点上的受控打包发布与 Windows 桌面自更新链路，包括制品绑定、独立安装确认、跨重启验收和失败恢复。

### Modified Capabilities

无。当前主规格目录没有 Kit／在线更新能力规格，本次新建上述单一能力，不修改 Harness 修复方案。

## Impact

- Kit 能力注册、编译模板、冻结执行计划、运行状态、能力确认与聊天状态投影；现有构建／发布 Kit 保持可独立运行。
- 发布中心向链路提供有来源的发布结果，更新管理器提供受限的精确制品暂存、归属预留和安装交接。
- Windows Tauri 更新助手、启动验收，以及 Kit 面板的计划与进度展示。
- 现有 Kit、发布、节点更新测试及隔离前端／Rust 夹具；不依赖真实上传或自我安装作为自动化验收。
- 本轮目标是已安装的 Windows 桌面执行节点。“本机”固定为 Session 所属的实际执行设备，不是控制窗口、默认节点或随连接切换的机器。Linux、Docker、跨节点批量升级和源码开发进程自替换不纳入新增能力，已有更新入口保持不变。
- 不自动创建并运行用户的生产 Kit，不触发真实发布、安装或重启；产品实施与实际运行仍是两个独立操作。
