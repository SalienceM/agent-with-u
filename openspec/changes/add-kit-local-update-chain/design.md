# Design

## Context

动机见 `proposal.md`。已有代码提供了可复用的基础，但不能仅增加一个安装命令：

- `workspace_kit_store.py` 的 DSL 已有 `kit_call` 和 `awu_capability`；`kit_capabilities.py` 仅注册 `release.publish_latest`，context 只包含发布服务、工作目录和 source。
- `BridgeWS._run_kit_capability_step` 将各能力统一视作发布作业，等待 start／poll 成功后推进；现有 phase、错误文案和 job 投影有发布专用假设。
- `release_center.py` 冻结完整 manifest，并同时上传不可变版本清单与通道清单，但 Kit 公共计划／作业投影未提供完整的不可变发布结果契约。
- `UpdateManager` 每个执行器只有一个状态文件和安装结果文件；当前结果按完成时间合并，没有 Kit run／step 绑定。`prepare_apply()` 返回 restarting；Bridge 把安装通知发给目标设备本地客户端。
- `api.ts` 仅处理 canonical local 来源的 `nodeUpdateInstallRequested`，这是防止误关远端控制窗口的重要边界。
- Tauri `run_update_helper` 在安装器接受退出码后写成功回执，再尝试启动程序；当前成功回执不是新版本启动证明。
- `ChatKitTools` 只允许全为发布能力的链路使用发布代确认；混入新能力后不能擅自放宽。`WorkspaceKitsPanel` 的确认视图同样需要按能力区分。

## Goals / Non-Goals

**Goals:**

- 将本次运行的构建、发布、安装与启动证据连为可审核、可幂等恢复的一条记录。
- 保留设备管理权限及人工安装确认，退出前把责任移交给独立更新助手。
- 未知结果只核对、不重放；普通 Kit、发布中心、更新中心仍能独立使用。

**Non-Goals:**

- 不开放任意 Bridge RPC，不提供通用跨节点更新能力。
- 不升级 Linux／Docker 或源码开发实例，不改 SSH 更新 Kit。
- 不扩大聊天发布代确认，不实现静默强杀业务任务、自动回滚或自动重复安装。
- 不在实现／测试期间发布真实制品或替换当前用户正在使用的应用。

## Decisions

### 1. 以白名单能力复用现有更新服务

新增拟定能力 `node.update_local_published`，仅允许 `target=executor`，采用设备更新管理权限与 mandatory human approval。将 UpdateManager 服务、真实设备身份以及当前 run 的只读发布证据解析器加入受控 context；能力不能调用任意 RPC，也不接受模型提供的绝对安装计划路径、程序命令或 owner。

第一版支持已安装的 Windows 桌面。预检证明目标设备有 canonical local Tauri 客户端、当前程序支持交接协议、目标制品声明匹配协议、当前用户有设备管理权限。多安装实例或多个可能接管客户端无法唯一确定时阻止交接，不广播到未知安装实例；计划绑定实际安装实例／进程归属，不借用默认节点。

备选：生成 Shell 调用安装器或借助普通 client command。未采用，因为缺少原生退出、跨重启归属及验收，也可能绕过产品确认。

### 2. 构建与发布结果按本次 run 关联

组合生成使用当前 Session 的真实 Kit 清单解析用户选择；默认模板为构建 kit_call、受控发布步骤、最后一个本机更新步骤。缺失／多个候选返回 needs_input；保存后不执行。更新步骤必须位于展开计划的最后，后面有命令或能力则拒绝，避免重启恢复时隐式执行额外工作。

构建步骤完成时记录本次构建候选的来源、版本／buildId、制品 ID、文件大小与摘要。对内置构建脚本的候选登记加入运行关联，并在执行器侧验证；不以“目录最新文件”或 exit code=0 单独证明本次制品。通用构建 Kit 缺少可核实制品输出时要求补全预览定义，不擅自改其原版本。新链路使用严格绑定模式，保留旧发布 Kit 的独立使用方式。

成功发布生成有版本的 `publishedRelease` 小型结果，由服务端从该 run 的真实发布步骤、冻结计划和成功 job 生成。包括发布 step／plan／job ID、计划指纹、版本／buildId／sequence、通道、不可变 manifest URL 和内容摘要、制品身份及安装兼容信息；URL 来源于已校验发布配置和 `versionedManifestKey`，不字符串猜路径。更新只引用同一 run 中前序成功发布步骤，不能接受用户填的“成功回执”。多个 Windows 安装器在更新计划中明确选择并进入新指纹，绝不静默选另一文件。

暂存使用不可变清单并核对发布身份和制品 hash，不再读取 stable 来决定对象；不修改节点日常更新配置。签名策略仍按节点要求执行，不为链路降低校验。发布后版本被保留策略清除导致对象缺失时明确失败，不改装最新版本。

备选：发布成功后调用 `nodeUpdateStage` 默认 latest。未采用，因为其他发布或 CDN 状态会使实际安装对象漂移。

### 3. 独立冻结安装计划和人工确认

准备阶段核对设备、发布结果、更新占用及兼容性，下载并校验本次制品后生成安装计划。计划显示具体设备／安装实例、当前与目标发布身份、平台／通道、制品、摘要／大小、预检和退出影响；凭据与完整环境不进入计划。Kit 面板按 capability 渲染发布或安装确认，不能复用“确认发布”文案。

确认增加可选协议化参数（计划指纹、requestId）并为新能力强制要求，旧发布调用保持兼容。审计绑定 owner、Session、run、step 和完整计划；重复请求返回原回执，作用域或内容变化拒绝。确认和交接时均重新检查设备权限及当前预检。

ChatKitTools 对该能力始终 `canApprove=false`，返回完整可审查计划和面板提示；混合链路保持现有不支持发布委托的安全边界，明确解释需在面板确认。不要把现有发布开关解释为允许安装或重启。定时运行遇到该能力直接拒绝，不进入无人确认安装。

备选：把发布确认当作整条链路授权。未采用，因为安装会中断本机且现有委托范围没有包含该副作用。

### 4. 节点级更新预留与短暂交接屏障

UpdateManager 新增按安装请求归属的原子预留，同一个节点只能有一个更新操作；普通更新中心与 Kit 共用预留，不覆盖他人的暂存／下载／安装记录。准备失败和交接前取消只清理本次请求；未知交接不能自动释放。

安装前检查权威任务注册表：聊天、LOOP、序列派发、其他 Kit、终端／受管任务、未确认退出等。自身已完成构建和当前更新步骤不计作阻塞，但发起聊天若仍在运行则保留为忙状态。忙时显示“请结束任务后重新确认”，不自动杀任务，也不后台等空闲后突然安装。

确认后在短暂节点交接屏障内重查忙状态并阻止新工作进入，落盘待交接记录后发送明确目标客户端通知。未交接且可证明助手未启动时释放屏障；交接可能发生则保留保护，启动恢复只核对。更新中心的并发 apply 也必须遵守预留，避免两个安装器竞争。

### 5. 持久化、幂等的安装交接和验收协议

使用受管 updates 目录下独立的版本化安装 journal，并将其关联同步写入 Kit step runtime。身份包含不可预测安装 requestId、owner、deviceId／安装实例、Session、run、step、计划指纹、制品 SHA-256、目标完整发布身份；journal 是安装责任来源，Kit 中是用户可见投影。先写 durable intent，再由助手领取一次性请求，最后确认交接；双文件更新失败不能启动安装或伪造已交接，恢复按同一身份核对。

建议状态如下，属于新增协议的 runtime phase，通用 run 增加对应非成功状态并适配所有 active 判定：

`preparing → staging → waiting_approval → handing_off → waiting_restart → verifying → succeeded`

分支保留 `blocked / failed / result_unknown`。handler 返回“已交接”后运行器暂停并持久化，而不是进入普通的“非 succeeded 即失败”或继续后续步骤。`kitResume` 对该类型只能恢复核对，不重走 start；未知结果保留保护且可显式只读核对，不能无限自动重试。

助手启动前重新检查托管路径、计划指纹、制品 hash、实例与归属；原子领取请求，重复通知不重复执行。仅等待／停止本次安装实例拥有的进程，不按进程名杀全局程序。安装器结果写独立 request 绑定回执，记录安装成功／失败；重启启动调用失败也写失败，不吞掉异常后假报整链成功。

新应用启动后，后台有界恢复同设备的待验收 journal，并由已认证本地桌面握手提交桌面实际发布身份，结合 Backend 编译发布身份和本地连接就绪完成验收。必须匹配 full buildId／sequence 等构建身份，不能只比较三段 MSI packageVersion。旧运行时没有该协议则未知，不从普通 install-result.json 的时间戳推导本次成功。首次核对自动、在限定时间内完成；超过时限标未知，后续由明确只读检查或真实启动事件重新核对，无安装重放。

兼容现有 helper 计划：新增关联段带协议版本，只有新 Kit 计划要求完整回执；旧更新中心计划仍按旧入口读取，不能用旧成功记录满足新 Kit 验收。发布制品登记增加更新验收协议元数据，拒绝链路安装不支持协议的版本，避免安装后无法恢复。

备选：安装器 exit code=0 即标 Kit 成功，或重启后继续全部未完成步骤。均未采用，前者缺少启动证明，后者可能重复发布或安装。

### 6. 取消、恢复和可见性

准备／下载／待确认阶段仍可正常取消。助手原子领取后进入不可保证撤回阶段，`kitCancel` 对该步骤返回明确“已交接，不能保证取消”的回执，而不是套用普通命令的立即 cancelled；不杀安装器、不自动回滚，不抹掉已成功发布。UI 根据阶段显示“取消”或“查看安装结果”，不能对不能撤回的操作显示已安全停止。

保留当前 Step 的阶段、时间、设备、目标版本、安装回执及启动验收证据，聊天 status 同步这些有限字段；退出／重连状态不得变成普通网络错误。维护大小限制与懒加载，不将凭据或全量日志加到紧凑推送。只核对当前 owner 的结果；重启后台可处理受管记录但不能向其他用户推送详情。

## Risks / Trade-offs

- 自更新会终止执行器和窗口 → 独立助手、持久 journal、原子领取和启动核对，不依赖原聊天继续存活。
- 安装与 Kit 状态无法跨文件原子提交 → journal 为责任来源，先 durable intent 再副作用，使用同一 request 身份恢复投影；未知不重放。
- 安装确认前后出现新任务 → 权威忙闲复核及短暂提交屏障，不能仅靠前端按钮禁用。
- 老安装器／旧版本无法回传验收 → 发布兼容元数据与预检阻止，既有更新中心手动路线保留。
- 初次使用功能需要先安装带新协议的应用 → 在文档明确引导；本变更不声称当前旧进程已具备新能力。
- 新增状态可能影响通用 cancel／resume／删除及聊天展示 → 集中状态判断、兼容测试覆盖旧 Kit，避免默默把未知当终态。
- 安装成功但重启失败没有可靠自动回滚 → 展示准确失败及既有手工恢复入口，不新增未经要求的破坏性回滚。

## Migration Plan

新增字段使用版本化协议；旧 Kit、版本账本和历史记录不重写。先实现结果绑定、更新预留／交接回执、恢复验收，再接入模板和 UI。发布新应用需要单独授权，通过既有更新中心或安装包完成首次部署；功能可用后，用户在 Kit 面板预览保存组合，不自动修改现有生产 Kit。

回退代码前必须处理所有已交接或未知安装，禁止通过降级解释器解除预留。未开始安装时可取消新组合并继续使用旧打包／发布／更新中心入口；已交接请求仅核对或按明确的人工恢复处置，不自动重装。
