# Design

## Context

参见 proposal.md。已有 Start 启动独立 Session，但只有一次 startRequestId，失败后不能继续，完成核对依赖可见前端。已有用户交互与权限组件可复用；不复用完整 useChat，因为其自动续跑及普通聊天输入不适合托管合并。

## Goals / Non-Goals

**Goals:** 同 operationId 的托管修复状态、事件驱动输出和请求内交互；后端实际退出衔接 Git 核对。

**Non-Goals:** 不改 Git 合并算法，不自动 apply/push/reset/stash/清理，不新增测试执行器或将模型声明转换成测试证据，不触发真实用户操作。

## Decisions

1. mergeRepair=1 能力门控。原 merge 行增加 repair（requestId、status、notice），保持原 sourceSessionId 写入归属。Start 接收回执与修复结果分离，旧 Start 回执仍可读取。每次显式继续用新 requestId，同 ID 永不重放。
2. 由 Start 监听权威 chat task 完成，在 registry 释放后保留一个 owned 后处理任务执行只读 Verify。活动/退出未知不推进；失败保留成果；实际 Git 条件未通过显示需继续处理。不会因前端关闭而遗漏核对。重启后以真实活动和保存状态做保守恢复，不自动运行模型。
3. 新关联修复读取接口校验原请求和整合工作区关联，返回最多 20 条近期可见消息、总计受限文本及当前权限计划；不包含隐藏思考和大附件。已有运行流仅投影最近文本/工具活动，按结束、权限、重连等事件重读；不做定时轮询。与昂贵 Git Inspect 分离。
4. 独立修复区复用 UserInteractionsPanel 和 PermissionGate，读取验证后绑定真实 executor，权限提交通过原请求校验。不出现普通新会话工具栏，不要求用户手工 Git 提交。高级详情保留直接会话入口用于旧记录恢复。
5. 主状态优先显示修复运行/待交互，整合目录的预期冲突和未提交内容归入修复区；来源/目标脏或发生变化仍是合并阻塞，不混为中间分支维护任务。

## Risks / Trade-offs

- [模型未完成修复或提交] → 真实 Git 核对拒绝就绪，原请求显式继续，不伪造完成。
- [原生进程退出未知] → 复用活动保护，显示未知且禁止重试，保留恢复入口。
- [已有 UI 改动] → 在当前分支列表、并发读取和确认流程之上增量实现，保留旧回归测试。
- [输出有界] → 近期记录覆盖常用审阅，完整历史保留高级入口；不声称项目测试已通过。

## Migration Plan

追加可选字段与能力，无数据搬迁。新前端在旧节点使用原流程并提示升级；旧前端仍可使用原 Start 接口和恢复入口。回滚界面不删除整合成果与记录。
