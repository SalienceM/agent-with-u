# Proposal

## Why

用户只想将 B 合并到 A，目前却必须理解并进入第三个整合会话，手动推进修复、提交和核对。合并请求应承担完整交互，让后台独立工作区成为执行细节。

## What Changes

- 在同一 B → A 请求内显式启动修复、查看有界进度、回答问题和审批；无需切换会话或手动提交中间分支。
- 托管修复调用负责解决冲突、相关验证和候选提交；实际退出后由后端核对 Git 并回到合并确认。
- 区分接收、运行、失败、需继续处理、未知和候选就绪；明确失败可在原请求继续，重复请求与重连不重放。
- 保留来源/目标保护和准备、应用两次独立确认；高级恢复入口与旧节点仍可用。

## Capabilities

### New Capabilities

- `merge-request-execution`: 原合并请求内托管修复、交互与结果衔接。

### Modified Capabilities

无。主规格中尚无合并能力；本变更增量衔接已完成但未归档的 `simplify-branch-merge-workflow`，替代其中必须打开整合会话的日常交互，保留其执行边界。

## Impact

涉及 project_merges 后端、合并流程控制器、请求面板、运行输出/权限/问题组件与隔离测试；新增能力标记与关联修复读取接口，无新依赖。不执行真实用户合并、不部署、不自动归档。
