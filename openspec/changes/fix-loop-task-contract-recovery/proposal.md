# Proposal

## Why

LOOP 会把“有执行步骤、但任务协议不合格”的计划先标为规划成功，随后将计划错误、历史阻塞无效及真实身份变化压成“任务映射/阻塞身份未确认”，用户反复运行仍可能回到“等待处理”。同一次暂停又以调度决定和进展守卫重复展示，既没有说明需要用户解决什么，也没有提供针对内部协议错误的有界恢复路径。

## What Changes

- 在接受规划、启动执行前统一校验步骤及适用的完整任务协议；可纠正的本次模型输出错误进入现有规划预算内的只读纠正，不另开无界重试链。
- 保留结构化校验原因，区分字段/任务映射错误、正式来源真实变化、执行身份变化、旧阻塞不可核对及实际授权/环境门槛，不再用一个泛化文案覆盖所有原因。
- 为已经暂停的无效协议提供显式、只读、有界的“修复任务映射”操作，保留原始记录、真实未解决阻塞和已完成步骤；修复成功也不自动恢复执行或开启 Auto。
- 同一暂停的决定、守卫和详情使用同一因果身份与修订，仅显示一个主问题，合并证据与影响范围；不同原因不按文字相似度合并。
- 处理面直接说明“系统正在纠正 / 纠正未成功 / 需要核对范围 / 需要用户输入 / 旧调用未退出”等真实状态，提供对应动作，保持恢复后的面板、流程、评分和直接控制入口。
- 增加协议纠正、预算耗尽、历史兼容、停止/迟到竞态和重复提示的假 Backend、持久化与浏览器回归。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `loop-continuation-decisions`: 新增任务协议前置校验、有界纠正、旧暂停显式修复和精确因果问题呈现要求；沿用既有授权、来源、任务验收与等待/故障分离规则。

## Impact

- 后端：`bridge_ws.py` 的 prepare/execute 边界与等待生成，`loop_task_blockers.py`、`loop_task_blocker_bridge.py` 的校验和归约，`loop_store.py` 及紧凑/详情序列化；复用原调度器和已有控制/来源/环境门槛。
- 前端：`loopWorkbenchView.ts`、`useLoopWorkbenchState.ts`、`LoopPanel.tsx`、`LoopTaskBlockerDetail.tsx`、`LoopContinuationStatus.tsx` 及 API/类型；不重做布局、不增加常驻配置墙。
- 验证：扩展任务阻塞、阶段审计、续跑和工作台回归，补充 `docs/loop-adaptive-delivery.md` 与必要项目约束说明；无新框架依赖。
- 依据：代码及合成用例已确认校验时序、原因丢失、旧无效记录无法自行修复和重复卡片问题；尚未读取截图对应生产 Loop #11 原始数据，不能断言该轮具体属于哪种校验失败。
- 非目标：不修改外部 Godot 工程、不访问真实用户存档、不操作生产 Session、不调整 ACL/PATH/节点/Backend 以绕过拒绝、不降低验收标准，也不修改普通聊天/apply 语义。
- 与未归档的 `refactor-loop-workbench`、`restore-loop-visual-experience` 兼容：本变更仅在现有续跑能力内增加恢复约束，保留视觉纠偏成果；后续同步按旧重构、视觉恢复、本修复的顺序核对。本轮只创建规划文件，不修改旧变更或主规格、不归档、不实施。
