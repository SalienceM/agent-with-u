# Design

## Context

动机和范围见 `proposal.md`；本设计基于当前脏工作区中的视觉恢复实现，不回滚或覆盖其他改动。

已核实的链路如下：

- `bridge_ws.py::_loop_audit_plan` 用 `bool(steps)` 接受规划；`_loop_do_prepare` 仅对无步骤输出重试，`_loop_do_execute` 才调用 `_loop_freeze_tasks`。
- `loop_task_blockers.py::freeze_plan` 已能检测完整正式任务范围、依赖、隔离前置与映射错误，但 `reduce_scope` 把无效计划、身份不一致和无效旧阻塞合并为同一个原因。
- `merge_blockers` 遇到无效历史聚合直接保留它。这保证了不丢阻塞，却没有独立的修复入口；新轮次不能解决历史协议自身的不一致。
- `_loop_wait` 同时保存决定和暂停守卫；`loopWorkbenchView.ts` 只有无进展等已有特定关联会合并，任务范围等待会成为两张卡片。
- `tests/test_loop_stage_details.py` 已覆盖三次规划及旧降级分支；`tests/test_loop_task_blockers.py` 已要求跨轮保留阻塞、只读复核和停止优先；这些保护不是待删除的行为。

截图只证明用户看到了泛化等待与重复提示，不能证明该生产轮次究竟漏了任务、发生身份漂移还是继承了无效阻塞。实现与验收使用合成数据，不依赖读取生产 Session。

## Goals / Non-Goals

**Goals:**

- 把可自行纠正的当前输出错误留在规划阶段，所有成功/暂停说明与执行端真实状态一致。
- 让有效任务图、历史阻塞及来源身份在同一套校验中保持一致，同时保留显式修复的审计轨迹。
- 用一种有修订的原因引用驱动摘要、计数、处理动作及详情，复用现有单控制器与懒加载。

**Non-Goals:**

- 不新增第二套 LOOP 调度器，不把用户点击修复解释为执行、接管或开启 Auto。
- 不把协议校验、模型复核或文件哈希当成任务验收或 OS 隔离证明；不为修复运行项目构建/测试。
- 不改变来源绑定/确认的权限与验收条件，不通过自动改绑、删除阻塞或采用模型声称的新身份来消除等待。

## Decisions

### 1. 用纯校验结果区分可纠正输出与真实边界变化

在 `loop_task_blockers.py` 提供统一的有界校验结果，保留现有 `valid` 和兼容原因文字，新增版本、稳定原因码、来源类别、字段定位、受影响任务、证据引用及可建议动作。桥接层补充真实身份和当前资格，模型不能提交或指定执行端身份。

建议类别与路由：

| 校验事实 | 处理路径 |
| --- | --- |
| 当前模型字段缺失、映射不一致、正式来源未变但模型漏列任务 | 同预算只读纠正；耗尽后提供定向修复 |
| 正式来源实质变化、来源不可核对 | 既有来源差异/核对路径，不自动改绑 |
| Backend、执行节点、访问策略、配置、控制修订等身份变化 | 说明变化维度，重新核对；不得由重写 JSON 接受新身份 |
| 无效历史阻塞聚合或原始证据不足 | 显式修复/补充依据，范围不明时继续保护 |
| 已有环境故障、显式暂停、旧调用未退出 | 保持原对应门槛，不归类为格式问题 |

纯函数区分 `plan_invalid`、`identity_mismatch`、`blockers_invalid` 等结构化事实，不能再先折叠成 `task_scope_unknown` 再靠字符串解析恢复原因。显示旧原因码仅用于向后兼容，不能驱动宽松放行。完整错误放详情；紧凑摘要最多 16 条字段诊断、16 个证据引用，任务列表沿用 `MAX_TASKS` 上限并明确未知/截断，不把截断列表当成完整范围。

替代方案：仅改中文报错可以改善文案但不修复时序；放宽任务校验会失去正式范围和阻塞保护，均不采用。

### 2. 将完整校验前移，合并现有规划尝试预算

规划候选先保存原文、解析和步骤校验，再使用当前来源快照、原始步骤与历史有效范围校验完整 `taskPlan`，最后才接受并冻结。新规划按适用协议要求完整任务图；正式完整台账与本轮步骤子集分开。缺少协议不能作为新输出逃回 legacy 的开关。

prepare 初次、prepare 重试和当前 execute 入口重规划共同使用一个持久化计数：总计至多 3 次。契约错误、步骤错误共用预算，不分别获得三次。每次纠正携带本次错误、当前完整正式任务身份、已冻结依据和未解决阻塞，不要求模型复述整个历史。所有纠正调用强制规划的 `read-only` 角色，沿用 `_loop_run_agent` 的访问请求、调用诊断、取消及终态处理；不额外套一层 Backend 自动重试。

有高优先级门槛时不纠正。预算内可纠正时状态是 `retrying`，不提前调用会关闭 Auto 的 `_loop_wait`；接受后只继续原授权迭代。失败耗尽转入一次持久化等待，保留 Auto 暂停，不因 stage 从 prepare 移到 execute 或新推送重置预算。错误结果不得走最小写步骤兜底。原有 legacy 降级分支仅适用于确实无新协议要求、无正式范围/未解决阻塞约束的兼容路径，并保持明确 degraded 标识。

执行入口保留第二次身份/原始步骤一致性核验，前移校验不能替代它。部分步骤已经执行后，不以重新规划改写原执行记录：保留已执行成果与未知结果，后续需要从受保护的新规划边界处理，不能重放写步骤。

替代方案：在 execute 再加三次重试会叠加预算且继续把规划显示为成功；失败后自动新建轮次会消耗预算并反复遇到同一历史问题，均不采用。

### 3. 旧暂停使用独立的显式修复动作，但复用执行控制边界

拟新增有界的 `loopRepairTaskContract` 请求与只读回执查询，服务于“修复任务映射”按钮，不调用普通运行 RPC 来代替。请求包含客户端 `requestId`、Session、目标问题/修订、round/seq 和预期控制修订；执行端从实际路由确定 owner/executor，从记录确定来源与访问身份，拒绝客户端伪造或过期对象。

修复复用现有 Session 运行登记、独占与控制权门槛，不引入新的后台调度器。只允许目标协议暂停下、无执行/接管/未确认旧调用且无更高优先级门槛的显式请求。目标协议等待允许进行修复本身，但不清除暂停；其他暂停不能通过此例外越过。记录受控操作状态、最多两次只读模型调用和有界回执；同请求幂等，同一在途对象不允许重复启动。接收成功不等于完成。

修复分为确定性核对、必要的只读候选纠正、确定性提交三段：

1. 从保留的原始阶段证据、原任务图、正式来源和未解决阻塞中核对可恢复范围；无信息可恢复时直接说明缺失，不浪费模型重试。
2. 必要时让模型纠正候选表达，最多两次；不能要求再次访问被拒资源或执行应用。模型建议不单独证明任务独立、旧阻塞解除或来源语义相同。
3. 完整校验通过且所有执行/控制/问题身份仍匹配，才保存带原问题和原记录引用的新映射。已有有效阻塞逐项保留，受保护任务取保守集合；无法确定的影响不凭空缩小。保留旧无效聚合的原始数据与原因，以修复记录建立替代关系，而非直接把 `valid` 改成 true 或删除它。

“协议修复成功”只表示表示层/映射一致性恢复，不解除真实任务阻塞。涉及改义、改依赖、范围变化或无法核对原始证据时，转入现有范围处置流程而不是提交修复。成功后仍暂停，返回“映射已修复，尚未运行”；用户随后通过原运行/恢复入口重新核对边界。普通运行遇到待显式修复的历史协议问题应返回该对象和动作，不新建相同失败轮次。

前端超时、断线或取消等待仅表示结果待确认；允许一次合并的只读查询/手动再查，无自动写重试或轮询。进程重启后对 running/unknown 回执不能重放；确认退出与记录身份后才能接受新的显式操作。新增字段通过 `loop_store.py` 和既有有序保存链持久化，不能覆盖并发 Addon、控制权或目标修订。

替代方案：自动迁移所有无效旧记录会把未知变成错误的有效；永远保留一个无效聚合并直接拒绝会形成无法恢复的永久暂停，均不采用。

### 4. 统一因果引用，不按文字去重

执行端产生有界 `causeRef`（问题身份与修订）供 decision、progress guard、修复状态共用，归属 owner/executor/Session/round/seq。相同暂停的重复保存和重复推送复用身份，新的原因或证据修订不得挪用旧动作对象。`_loop_wait` 保存一个原因事实，各投影仅引用它；详情保留原决定与守卫证据。

前端 `loopWorkbenchView.ts` 只合并相同当前身份和因果修订的卡片，合并 refs 与 affectedIds，并保留最严格的真实门槛及其解释。不能让先插入的普通卡片覆盖更重要的退出未确认动作。来源/环境现有精确引用合并继续有效，不能改成 `reasonText` 或通用 reasonCode 去重。

旧数据没有新引用时，只有原记录已有明确决定关联且完全匹配才能投影合并；否则保留“旧记录关联未确认”，不回写或伪造原因身份。历史详情保留当时事实，不混入新修复结论。

替代方案：隐藏所有守卫卡片会丢独立问题；按文案合并会把真实独立阻塞混为一谈，均不采用。

### 5. 交互保留主视图，问题处理只提供相关动作

继续共用 `useLoopWorkbenchState`。主面只显示最需要处理的原因和计数，处理面承载错误字段、任务编号、纠正次数、原始依据入口和定向动作。状态与按钮示例：

| 状态 | 反馈/动作 |
| --- | --- |
| 同轮正在纠正 | “正在纠正任务映射（第 2/3 次）”；保留停止和原始详情 |
| 内部纠正耗尽 | “任务计划仍不合格”与具体缺项；符合资格时“修复任务映射” |
| 显式修复成功 | “映射已修复，尚未运行”；保持原运行/恢复入口与现有 Auto 值 |
| 真正范围变化 | “任务范围已变化”；定位范围差异确认，不建议反复运行 |
| 旧证据不足 | 列出不可核对项；进入目标/补充或来源处置，补充本身不放行 |
| 退出未确认/离线/旧端 | 明确原因和只读证据/回执入口，不显示为可强行恢复 |

修复动作与运行资格分开；按钮标签不能承诺放行。按问题与修订加载详情，问题更新后旧表单失效，迟到响应只留原对象。桌面和窄屏继续使用现有有界辅助面板、焦点返回与 Escape 行为；不增加新的常驻设置区。

替代方案：只新增“按原条件再试”仍然缺少作用对象，无法解释到底重试什么，不采用。

## Risks / Trade-offs

- [协议纠正仍依赖模型] → 明确 3 次规划总预算/2 次显式修复上限，接受条件为确定性校验，不以模型“已修复”文字放行。
- [历史数据不足以安全恢复] → 这是可说明的真实限制；提供缺失证据和范围处置入口，不承诺所有暂停都能自动解决。
- [校验与执行间身份变化] → 调用前后以及提交/执行边界均核验冻结身份；迟到候选只进入原审计。
- [保存修复覆盖并发状态] → 复用共享状态和有序写入，测试 Addon/目标/控制修订变化，提交失败不得提前发布成功。
- [read-only 在不同 Backend 的隔离程度不同] → 复用真实访问策略，能力不支持或拒绝按现有环境门槛失败，不换宿主、节点或更高权限重试。
- [协议详情过大或包含敏感值] → 原文沿用受限懒加载审计，紧凑字段有数量/长度限制，身份仅公开维度而非配置值。
- [用户重复点击耗尽成本] → 同请求幂等、Session 独占、结果待确认时禁止重复提交；再次显式请求才产生新有界操作，不自动循环。

## Migration Plan

1. 在当前工作区增量实现新校验/原因字段与回执；缺字段保留旧行为和未知值，不批量改写已有阶段文件。
2. 先验证服务端边界，再接入前端动作与因果合并；混合版本客户端/执行端不支持修复时只显示不可用，不降级成运行。
3. 用 fake Backend、隔离临时阶段文件和浏览器夹具覆盖协议、持久化、并发及桌面/窄屏场景；不启动真实 Godot，不调用付费模型或干预生产 Session。
4. 后续发布时由用户按正常维护流程处理受影响运行；本变更不会自动恢复旧暂停。部署失败保留新字段和原证据，禁用新动作；旧版本不了解修复回执时不得自动恢复或重放此类记录。
5. 规格同步顺序为 `refactor-loop-workbench` → `restore-loop-visual-experience` → 本变更。本变更只给主能力追加要求，不改写旧工作台同名条款；同步时核对已新增要求，避免重复追加。本轮不执行同步、归档或发布。
