# Design

## Context

动机见 [proposal.md](proposal.md)。以下是只读源码检查所得，不代表已经测得用户现场的耗时或根因：

- `LoopPanel.tsx:378` 的接管仅设置共用 `busy`，按钮仍显示“人工接管”，没有操作阶段；异常路径没有 `finally`。面板入口部分原因只有 `title`，流程入口缺少同等解释。
- `App.tsx:852` 的交还先查主调用、再发 `loopRelease`；唯一“交还中…”位于可关闭的菜单，`manualLoopReleaseBusy` 是 App 级布尔值。成功提示没有 Auto 信息，菜单“恢复自动流程”容易让人误以为已开始执行。
- `api.ts` 的两项转交使用普通 `call()`，没有传请求超时；`Conn.request` 只有显式传入 `timeoutMs` 才启用期限。普通 call 失败可能返回 null，当前封装会把 JSON null 当作合法结果返回。
- `bridge_ws.py:5315/5381` 的同步 handler 在事件循环中执行。接管调用 `git_snapshot`，必要时调用目录复制；交还在 `_sync_manual_loop_record(finalize=True)` 中调用快照。Git 探测以外的多数子进程及目录复制没有整体等待边界。这是可能导致整个节点反馈迟滞的代码路径，不是现场性能结论。
- `LoopStore.save` 还会同步序列化整份状态、fsync 和更新 meta，不能只将快照移出事件循环却忽略转交受理/提交的落盘等待。
- `_loop_payload.canTakeover`、按钮判断和实际 handler 判断分散；实际接管另有环境活动保护，且 loopout 的可接管规则单独存在。应统一来源，而不是让前端重新猜测。
- 当前生命周期测试覆盖空人工轮、旧 streaming 残留、loopout 新人工轮和真实主调用拒绝；浏览器测试覆盖元数据恢复、只读人工总览，缺少完整的慢转交、丢响应及反复点击链路。
- 必须保留单例 LoopState、轻量元数据路由、按需历史详情、Session 所属执行节点和原生活动锁。此前归档的原生故障分类 WARNING 不在本变更内。

## Goals / Non-Goals

**Goals:**

- 以一个转交状态源连接入口、执行端回执和目标界面，任何等待都能解释且不会误报成功。
- 把慢 I/O 与状态提交分离，消除转交占用事件循环的路径，同时防止异步化引入并发写入或重复人工轮。
- 对慢响应、丢响应、重连和混合版本提供可测试的处理规则，不依赖真实模型完成速度。

**Non-Goals:**

- 不新增“运行中强制接管”“交还并自动运行”“取消后台转交”按钮；不扩大现有接管条件，不跳过未退出调用或快照保护。
- 不重写全局调度器、所有 RPC 或所有快照调用点；只处理转交路径及必须遵守转交锁的冲突入口。
- 不改变文件快照包含范围、Git 索引/HEAD、回滚或清理规则；不自动清空序列、安装工具或提高权限。
- 不将本次规划当作部署授权，也不在真实 Session 上做破坏性或付费模型测试。

## Decisions

### 1. 共享、按会话隔离的反馈，不再依赖两个局部布尔值

新增共享转交状态管理及展示组件，键为当前用户身份、执行节点和 Session。`LoopPanel` 面板/流程/loopout 入口、`App` 的人工菜单和 `ChatPane` 的常驻状态条订阅同一状态。状态条放在会话内容顶部，不随菜单关闭消失；保活 Tab 保留原操作，切换会话不把全局 busy 带到新会话。

入口保留接管确认及 loopout 新轮目标确认。用户确认后的下一次可渲染更新显示提交中；隔离浏览器夹具以 200 ms 内出现反馈作为交互验收预算（不包括系统确认框停留、隐藏 Tab 和后端响应时间）。不用预先切换控制权换取“快”。

| 状态 | 面向用户的反馈 | 可用动作 |
| --- | --- | --- |
| sending | 正在申请人工接管 / 正在申请交还 | 查看当前会话；禁止重复提交 |
| accepted / running | 正在核对条件 / 保存工作区快照 / 整理人工记录 / 提交切换，附耗时 | 查看状态；保持冲突保护 |
| reconciling | 响应超时或连接中断，结果待确认 | 检查状态；不直接重发 |
| committed + loading-view | 已接管/已交还，正在加载聊天/LOOP 面板 | 只允许重试目标界面读取 |
| succeeded | 已人工接管，Auto 已关闭 / 已交还 LOOP，Auto 仍关闭 | 正常人工操作或独立的现有运行入口 |
| blocked / failed | 原因、是否改变控制权及下一步 | 导航聊天/队列/详情；条件处理后重新申请 |

阶段停留 5 秒后显示“耗时较长”，仅用本地计时更新耗时，不通过计时器查询后端。成功反馈按操作身份去重；错误/未确认信息持续保留直到解决或用户收起详情。状态用 `role=status` / `aria-live=polite`，确定错误用可读告警，不能只以颜色和 hover 区分。

替代方案：只改按钮文字和 Toast 改动较小，但无法跨卸载/重连，也解释不了真实慢阶段；全屏遮罩会阻塞无关会话，均不采用。

### 2. 执行端统一资格判断与紧凑操作协议

提取无副作用的控制权资格计算，返回动作、allowed、稳定 reasonCode、用户说明、下一步和当前 controlRevision。覆盖 `loopidea`、运行中、resumable、loopout、真实聊天任务、人工消息/待发序列、环境检查及未确认退出等现有门槛。同一计算用于轻量查询和写入口，实际提交前再检查；空接管立即交还的特例保持。

新增 `loopControlGet(session_id, request_id='')` 和 `loopControlRequest(session_id, payload_json)`。只由现有 Session 授权、执行节点路由访问，不做任意 RPC 转发。

- request 输入：`requestId`、`action=takeover|release`、`expectedControlRevision`、仅用于 loopout 接管的可选 goal。服务端核对身份、动作和有限输入，不接受客户端声称的 allowed。
- 查询/响应摘要：`protocolVersion`、`controlMode`、`auto`、`stage`、`round`、资格说明及 operation。operation 包含 requestId、动作、原/目标模式、status、phase、revision、开始/更新时间、reasonCode、有限说明、checkpointAvailable、是否已提交及结果 controlRevision。
- 新请求持久化受理并注册单一 worker 后返回 accepted，accepted 不代表模式已变。真实阶段和终态通过现有 `loopUpdated` 的有界字段推送；`loopControlGet` 能补回丢失推送。
- 无模型正文、快照文件清单、原始异常、环境变量或工具租约进入该协议。每会话只保留当前操作和最近 8 项终态回执，紧凑推送只带当前/最近一项，不载入历史正文。

新增 `controlRevision` 与操作回执由 LoopState 持久化，必要的摘要同步进 meta sidecar；旧字段缺失按 revision=0、operation=unknown 加载。现有 `loopControlMode` 仍为已提交模式，而不是申请目标。

每个新受理操作和最终控制权提交均推进单调修订；阶段更新使用操作自身 revision。重复请求返回原回执而不推进修订，worker 核对受理后的修订。记录裁剪不能让旧 expectedControlRevision 再次取得执行资格。

替代方案：只靠本地超时无法判断请求是否已成功；只依赖现有 loopUpdated 没有操作身份，不能安全去重。单独引入通用任务系统范围过大，采用本能力的有界回执。

### 3. 单一预留、快照工作器和原子逻辑提交

在事件循环中检查资格并获取 Session 级转交预留，受理时冻结源 controlRevision、stage/round、工作目录、人工消息边界和相关修订。同一 requestId/同一输入返回同一回执；同一 requestId 不同输入拒绝。不同请求竞争同一 Session 时返回当前操作及 busy/conflict，不新建第二个 worker；回执已淘汰但 expectedRevision 过期的请求仍不可执行。

所有与转交冲突的入口必须检查该预留：主聊天发送/序列领取、LOOP 手动及 Auto 启动、相反转交、阶段/目标变化和环境复查。预留只阻止新冲突操作，不取消已存在调用；已有调用必须先满足原资格条件。状态查询、无关会话和只读查看保持可用。

仅将不可变输入的快照 I/O 放入工作器；不能直接 `to_thread(_rpc_loopTakeover)` 或让线程修改共享 LoopState。人工记录整理先生成待提交结果，不提前标记 record.completed。非 Git 目录复制在工作器执行；Git 进程使用受控调用及有界等待，保留临时索引策略。切换前后仍遵循既有快照策略：确认为失败后才允许既有 fallback/空检查点降级，并在成功回执中显示警告，不暗中省略快照以加快切换。

工作器整体超过 60 秒标记慢阶段/收尾待确认，停止启动新的快照阶段；这个时间是等待预算，不是“已杀死进程”的证明。线程或拥有的子进程未确认结束时保留预留并显示可查询状态；不通过取消 future 伪造退出，不按进程名称杀进程。关闭客户端不会取消 worker。本次不新增用户级取消动作。

I/O 返回后在事件循环重新核对冻结身份和资格，基于当前单例合并提交，而不是写回一个过时的整份 state 副本。loopout 的 round+1、manual record、control_mode 和成功回执一起写入 LoopStore 的同一次权威提交；失败不得提前留下 round+1。接管成功设置 auto=false；交还不启动任何调度。

转交落盘也走异步、有序的持久化边界：事件循环冻结待写数据，工作器只负责序列化和原子文件替换，完成后才发布权威新模式。以 Session 为单位串行化写入，不能在事件循环同步等待工作线程持有的 Store 全局锁。提交期间来自 Addon/旁路记录的更新必须按修订合并并有序落盘，不能被旧快照覆盖；把现有同步保存与转交写入的交错纳入回归。只读查询使用最后已提交元数据与在途操作摘要，不能暴露尚未持久化的目标模式。若这条混合保存路径无法保证一致，保留阻塞并停止 apply，不可直接把共享 state 交给线程。

权威记录提交后再更新 Session mirror、发推送。mirror 失败属于“已提交，界面待同步”，后续 get 修复 mirror，不能再执行一次转交。落盘失败保留原模式和失败/未确认状态；不以乐观前端状态掩盖故障。

替代方案：先切换再异步补快照会开放冲突写入；整段 handler 放线程会与单例状态竞态；取消等待后直接解锁无法确认旧 I/O 是否仍在运行，均不采用。

### 4. 有界等待与重连核对

新协议调用使用严格的 Session 所属执行节点和包含连接 readiness 的 12 秒客户端 deadline，不使用 home mock 或其他节点 fallback。空值、格式错误和异常统一成结构化客户端错误，所有发送路径都有收尾处理；request timeout 进入 reconciling，不当作已失败。

客户端保留原请求最小身份（不保存 goal 正文或工具授权），重载优先通过所属 Session 的 `loopControlGet` 找回当前操作。以下触发至多一次合并的状态读取：首次进入、执行节点重连、从其他 Tab 返回、发送结果未知，以及显式“检查状态”。无常驻定时轮询；并发读取合并，generation/revision 屏蔽过期结果。状态查询再次失败结束本次等待并显示离线/未确认，不继续旋转。

服务端重启后，从持久化控制权与回执判断是否已经提交。未提交但工作器退出可证明时标记 interrupted 并恢复原控制；退出未知则保持 unresolved 保护，不能仅因进程内注册表为空就宣告安全。恢复读取从不重放写操作。

替代方案：自动重复 POST 可能重复人工轮，按超时时间猜测成功可能允许冲突写，持续轮询会放大慢节点负载，均不采用。

### 5. 控制权已提交与界面就绪分开

通过现有 SessionRoutingCache 的修订机制集中应用 RPC/get/push 回执。一次转交只更新所属目标，只有其仍是当前可见会话才切换视图或聚焦输入框。迟到旧回执可保留在原会话，不抢焦点、不关闭其他会话的菜单。

takeover 后 `ChatPane` 走现有轻量元数据及聊天水合；release 后走 LOOP compact state。水合失败显示独立重试，不再次调用 takeover/release。完成推送和成功响应互补，但更老的 operation/controlRevision 不能覆盖新模式。LOOP 总览仍保持 inspectOnly 语义。

交还成功明确展示真实 auto 值；正常路径因接管已关闭 Auto，文案为“已交还 LOOP，Auto 仍关闭”。对于旧数据或其他控制端合法更新，按权威值说明，不能硬编码“已恢复自动运行”。运行下一次和开启 Auto 是独立用户动作，仍受原有环境、来源和权限门槛约束。

### 6. 混合版本与验收

新前端先从只读能力/元数据获知 protocolVersion；明确不支持时才进入旧接口模式，显示“执行端不支持阶段详情”。旧调用也要有本地反馈、有限 deadline、null 防护和事后控制权核对。不能在新版写请求未知时回退旧写请求。

旧 `loopTakeover` / `loopRelease` 保留参数和终态返回约定，以适配器调用同一服务并等待终态；不能把 accepted 包装成旧 status=ok。旧客户端没有 requestId 时仅在当前在途操作范围合并相同动作，仍受权威控制权及修订保护。如果旧同连接暂不能接收后续请求，新客户端采用“受理即返回”的新协议避免该限制。

验收必须覆盖 8 条规格要求的所有场景：

- Python：资格表与实际写入门槛一致；人工消息/队列边界；同 ID 重放与冲突；loopout 只增加一轮；快照延迟时无关轻量 RPC 在受控夹具中 1 秒内回复；落盘/镜像失败；重启未知 worker；I/O 未退出不解锁。通过注入慢快照和 fake backend，不调用真实模型。
- 前端单元：状态归约、操作/会话/节点隔离、相同推送去重、超时不是失败、旧 revision 不覆盖、有限重查和旧协议选择。
- Playwright 桌面/移动端：确认后下一次渲染有反馈、入口禁用原因、菜单关闭仍可见、慢阶段、返回目标视图、双击、断线/丢推送/丢响应/目标加载失败及无自动模型调用。复用独立 `.qa/home/typical`，执行前核对目录不是实际用户数据或链接。

## Risks / Trade-offs

- [异步化引入检查与提交之间的竞态] → 在同一事件循环预留，冲突入口统一门槛，提交前再验证；worker 不修改共享状态。
- [本机磁盘本身卡死无法保证快照按时退出] → 保证节点网络处理可继续、反馈真实；超时仅进入未确认，不能保证无条件快速转交。
- [LoopStore 和 SessionStore 不是跨文件事务] → 以 LoopStore 中模式+回执为权威，Session 元数据作为可修复镜像；测试提交后中断恢复。
- [旧客户端仍发同步语义 RPC] → 保留适配器并测试终态约定；新前端使用新版异步受理协议，不强制一次性升级全部控制端。
- [状态文本泄露错误上下文] → reasonCode 白名单、有限用户说明，不回传原始异常、文件清单、消息正文或租约。
- [快照过程中外部程序修改同一工作目录] → 保持已有快照保证，不声称新增跨进程文件系统事务；本变更只排除本 Session 的冲突调度。

## Migration Plan

1. 先添加向后兼容的状态字段、资格计算、操作服务和旧接口适配器，旧记录按未知加载，不自动运行迁移任务。
2. 再接入前端协议探测、共享状态及反馈；保留明确旧协议降级路径，更新人工接管使用说明。
3. 通过隔离契约、响应性、桌面/移动端及构建检查后交付。生产升级或重启须另行授权，不在此次 propose 或默认测试中执行。
4. 回退优先回退前端；后端回退前确认没有在途转交。若有 unresolved 任务，先按拥有关系核对退出和提交状态，不删除回执/活动锁来强行降级；保留旧字段与人工记录。
