# Proposal

## Why

人工接管和交还 LOOP 缺少持续、可解释的反馈：用户不能区分按钮不可用、请求已发送、保存快照、切换完成和结果尚未确认，容易反复点击。当前切换还同步执行工作区快照，可能阻塞执行节点事件循环；只增加加载动画不能解决这一等待体验。

## What Changes

- 为人工接管、loopout 开启人工轮、交还 LOOP 提供一致的操作状态：立即响应点击，持续显示实际阶段、耗时、失败原因和可采取的下一步；菜单关闭后状态仍在会话内可见。
- 使用执行端统一的可操作性判断，禁用按钮旁直接解释运行中、断点未完成、旧调用未退出、待发序列或离线等原因，不只依赖鼠标悬浮提示。
- 将切换中的快照等阻塞 I/O 与事件循环分离，并以会话级互斥、修订校验和幂等请求避免重复人工轮、并行切换及异步提交覆盖新状态。
- 将请求受理、服务端控制权提交、客户端界面恢复分开。超时或断线显示“结果待确认”，重连后核对原操作，不盲目重复提交；成功响应和推送任一路径均可促成一致界面。
- 交还后的反馈明确“已返回 LOOP，Auto 仍关闭”，提供独立的现有运行入口；接管仍关闭 Auto，交还本身不启动模型、不清空队列、不自动终止工作。
- 增加桌面/移动端慢响应、失败、重连、多控制端重复点击、迟到结果及执行端响应性的隔离回归。

## Capabilities

### New Capabilities

- `loop-control-handoff`: 人工与 LOOP 控制权转交的操作反馈、可靠回执、恢复核对及并发保护。

### Modified Capabilities

无。现有 `loop-continuation-decisions` 的授权/恢复/Auto 边界和 `loop-execution-environment` 的活动检查、退出确认约束保持不变；新增规格只补足控制权转交，不改自动任务调度或环境就绪的验收标准。

## Impact

- 前端：`LoopPanel.tsx`、`App.tsx`、`ChatPane.tsx`、`api.ts` 及 Session 路由缓存；新增共享转交状态与反馈组件，保持面板/流程和轻量元数据恢复一致。
- 后端：`bridge_ws.py` 的 takeover/release、快照边界和调度入口，`loop_store.py` 的有界操作回执及元数据；扩展 RPC/推送字段并保留旧调用兼容。
- 测试与说明：`test_loop_lifecycle.py`、新增转交契约/响应性测试、`session-recovery.spec.ts`、独立转交浏览器测试，以及用户手册的人工接管说明。
- 无新增模型调用、无第三方 UI 依赖；不调整权限、工作区快照范围或回滚规则，不处理此前归档的原生错误分类告警。本轮仅产出规划，不部署、不重启、不操作真实 Session。
