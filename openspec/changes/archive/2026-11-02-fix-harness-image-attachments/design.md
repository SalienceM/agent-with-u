# Design

## Context

动机见 `proposal.md` 的 Why；验收以本变更的 `specs/deepseek-harness-backend/spec.md` 为准。本设计基于锁定的 Python SDK `0.2.1rc3`、runtime `0.2.1-rc.3` 和源码提交 `1f81c047fc48fa190a683e469daa699857e9afe8`，不是生产模型识图验证结果。

当前链路存在几个必须一起处理的边界：

- `deepseek_harness_turn.py` 在启动 worker 前无条件拒图，随后只构造 text 内容块。锁定原生 SDK 实际支持 `{ type: "image", data, mimeType }`，并通过原生 attachments 服务将其保存为持久引用。
- `awu/capabilities` 目前只有身份、版本、实时事件与审批能力，没有图片能力。原生 `resolveModelInfo` 能返回 `inputModalities`，但未知模型的默认 text-only、内置目录和服务端目录会归并，单看结果不能证明能力来源；自定义地址还可能沿用内置模型名及默认声明。
- 原生 LLM 层会将 text-only 路线中的图片投影成省略说明。`prepareCall` 则能冻结实际 adapter、模型元数据和一次性 stream。图片准入必须发生在该投影之前，不能只检查 SDK 是否接受 JSON。
- rc.3 原生 adapter 在模型请求前尝试 Files 上传；配额错误会进入 `DeepSeekFileStore.reclaimOldestOwned()`，按 `dsh-` 前缀从当前 API-key 命名空间选择旧文件 DELETE 后重试，随后才可能 inline fallback。锁定源码 `packages/llm/llm-deepseek/src/file-store.ts:231`、`:291` 及隔离原生测试已复现对另一 Session 模拟文件的删除。`fileQuotaCleanupBatch` 在 `config.ts` 中要求正整数，不能设 `0` 禁用。复现只涉及本地假服务，不构成真实远端删除或清理授权。
- Python SDK 接缝和 AWU 桥目前限制 1 MiB；桥只检查通知 params，没有完整覆盖响应包及原生 transport 的逐行缓冲。原生输入和回传事件必须一并纳入预算。
- `BridgeWS` 的 `sendMessage` 是 fire-and-forget，先创建可见消息，再异步运行 Backend。普通图片解析会跳过坏条目；模型图片还可能包含 Prov 注入的视觉证据。`ChatInput` 的发送和排队回调均未等待准入回执便清空草稿。
- Harness 已有 owned worker、原生关联持久化及未知退出保护；这些不是新的图片通道可以绕开的边界。

## Goals / Non-Goals

**Goals:**

- 在现有 BridgeWS、owned worker、单条原生 JSON-RPC 连接上补齐图片准入和传输，不增加第二个模型调用通道。
- 让能力、请求回执和草稿分别有明确的身份与生命周期，能够区分“未提交”“已排队”“原生已接收”“执行失败”和“结果未知”。
- 将图片内容与控制元数据分开：消息及原生附件保留图片，能力、回执、错误和 trace 不复制载荷。
- 启用图片前证明能够阻止原生上传、配额恢复及后续生命周期中的未授权远端删除；能力支持与副作用许可分别核对，安全保证缺失时 fail closed。

**Non-Goals:**

- 不建设全局模型目录、自动识图探针或附件上传服务，不给用户增加手填“支持图片”的放行开关。
- 不修改 SDK 版本、上游源码或用户连接配置，不把本设计中的本地验证等同于发布或本机更新。
- 不替换其他 Backend 的发送协议，不实现旧诊断变更的通用预检工程。实际连接身份解析仅服务于本次图片准入。
- 不建设远端文件清理或清理授权界面，不自动索取删除权限；本次方案确认、图片发送、附件内容及旧工具／Kit 权限均不是远端删除授权。

## Decisions

### 1. 在实际执行器上形成带来源的三态能力证据

新增独立的 Harness 图片策略模块，并在 AWU 桥协议中增加版本化的 image-admission 扩展。沿用原有协议版本与核心握手，另带扩展版本、图片限额和传输限额；旧桥缺少扩展时只拒绝图片，不通过扩大兼容范围假装支持。

图片能力不是 Backend 配置中的布尔值。每次实际发送冻结以下身份：owner、executor、AWU Session、Backend ID、配置指纹、runtime/source/bridge 版本、本轮 provider/model、原生 Session 和 generation。配置指纹涵盖最终生效的连接和凭据作用域变化，但不向前端、日志或 trace 返回密钥及原始环境。地址必须来自本次原生连接实际使用的配置和环境优先级，不能只比较 UI 中的 `baseUrl`。

在本轮 owned worker 初始化、核心握手及配置完成后，调用新增的 `awu/imageAdmission`。该请求只接受被冻结的身份、有效路线及受控图片摘要，不携带用户任意 URL、路径或能力声明。能力判断同时要求两类证据：

1. **当前端点的明确声明**：在执行器原生桥内，通过当前已配置的连接及其原生凭据解析获取 `/models` 元数据。采用锁定运行时已有目录契约，匹配精确 model ID、显式 `input_modalities` 及 `api_capabilities.anthropic_messages`。只读取当前连接对应的同源目录；禁止重定向、地址探测和模型推理请求。单次读取最多 5 秒、正文最多 1 MiB；同一 generation 合并在途读取，不后台轮询、不跨 generation 复用成功结果。缺字段、未列出当前模型、读取失败或仅有模型名均为 unknown，不能套用原生默认值。
2. **当前原生 adapter 的能力**：用同一 provider/model 的 `resolveModelInfo` / `prepareCall` 核对原生通道是否支持 image，并遵守原生客户端版本及模型准入限制。端点声明 image 但锁定 adapter 无法传图，也不能放行。

此处是有界的单路线准入查询，不暴露完整模型发现 UI。元数据请求留在原生受信扩展内，不经前端传递 API key，也不借用其他 Backend 的配置。对自定义端点，不能沿用同名官方模型的能力：若其不提供可核对的目录声明，保持 unknown。隔离测试服务必须提供同样的目录契约，不增加生产可启用的测试放行参数。

返回值只包含 `supported | unsupported | unknown`、受控 reason code、来源类别、路线身份及适用限额：

- 两类证据明确允许图片：supported，文案为“当前路由声明支持图片”，不是“生产识图已验证”。
- 端点明确只接受文本或原生通道明确不支持：unsupported，并区分端点限制与运行时限制。
- 缺失、无效、不一致或无法取得证据：unknown。节点离线、旧节点缺少扩展单独说明，不泛化成缺依赖。

上述三态只描述图片能力，不覆盖远端副作用许可。`supported` 不能绕过下文的删除防护；若防护未验证或已失效，以独立的受控安全原因拒绝，不将已知能力改写成“不支持图片”或“缺少 SDK”。

仅查看界面或选择 Backend 不启动 worker、不查询模型服务，也不在输入区增加能力说明。实际发送总要重新核对，拒绝时通过既有错误反馈说明原因。下一轮模型覆盖或连接改变不能影响已经冻结的当前轮，也不能继续使用旧结果。

**理由与备选：** 单凭 SDK schema、模型名或内置目录即可放行最简单，但会把自定义端点与官方端点混同，也会把默认值当证据。发送一张探针图片会产生额外模型调用和隐私成本，因此不采用。目录不可用时保守拒绝是明确的兼容性代价。

### 2. 原生提交前校验，并在最终分派前阻止静默降级

只有图片校验、路线准入、远端删除防护和桥资源均通过验证后，才将 `if images: raise ...` 替换为“图片校验 → 当前路线及副作用安全准入 → 原生内容块构造”。沿用唯一 owned worker，不为预检新建另一个 Harness 会话或线程。

`awu/imageAdmission` 成功后，桥记录仅对本次 generation、路线、图片摘要和配置修订有效的一次准入。转发 `session/prompt` 前再次核对摘要、配置和身份；有变化则在调用原生 handler 之前拒绝，不保存部分图片或发送剩余文本。桥主动返回的前置拒绝使用受控结构化结果，不能通过解析原生异常正文推断“肯定未接收”。

最终 LLM 分派增加受信、会话范围内的图片守卫，覆盖当前输入及恢复后仍会参与模型调用的历史图片。守卫使用锁定运行时的 `prepareCall` 冻结 adapter 和元数据，并只分派这个 prepared handle；不能“查询一次能力，再调用可能重选 adapter 的普通 stream”。实现放在 AWU 的 `llm/stream` 适配层，使用请求范围的一次性上下文处理 prepared stream 重新进入同一 waterfall 的情况；不得用进程全局 skip 标记或修改 SDK 安装包。契约测试必须证明不递归、没有第二次 provider 请求，也不能绕过其他权限／工具中间件。

每次原生调用的 provider/model 必须符合本轮冻结路线；配置或 adapter 变动使准入失效时明确失败。若输入已由 SDK 接受后才发现变化，记录为“已接收后失败”，不恢复为“从未发送”。不能调用原生 text-only 投影、删图重试、切 Backend、OCR 或另建线程兜底。

原生内容按本轮输入构造：有文字时一个 text 块，随后按原顺序放全部 image 块；纯图片不增加伪造用户指令。图片使用本次已提供的字节，交给原生 attachments 服务持久化及恢复，不改成 skill-images URL。既有 Skill 的图片引用说明不能代替原生块；用户可见附件与 Prov 模型专用图片分开，后者同样经过校验和总量限制，但不得进入用户草稿恢复。

**理由与备选：** 只在前端或 worker 启动前校验无法覆盖异步配置变化及续聊。自行构造供应商 HTTP 图片请求会绕过原生恢复、权限和工具链，因此保留原生 session/prompt 与 adapter。

#### 远端清理是独立安全边界，不随图片准入放行

原生 attachments 的本地持久引用、Files 远端上传和 Files 远端删除是三个不同副作用。用户授权发送图片可以进入已核对的原生上传／模型传输路径，不能因此清理当前凭据可访问的文件。`dsh-` 前缀既不能证明当前 AWU Session 归属，也不是删除授权；即使有本 Session 上传记录，也不能代替独立删除授权。本变更的图片流程不提供远端删除授权入口，因而不得发出远端清理请求。

安全隔离接缝必须位于受信 AWU 适配边界，绑定实际 owned worker、原生路线和运行时资源，在潜在删除到达服务前阻止它，并覆盖当前图片、历史图片恢复、原生重试以及失败／停止路径。不能依赖“配额通常够用”、Files 返回 404、独立 DSH_HOME 或修改文件名前缀来证明安全；这些都不隔离同一 API-key 下的远端文件。也不能设无效的 `fileQuotaCleanupBatch=0`、改 SDK／上游源码、直接补丁生成 bundle 或另建供应商模型请求通道。

具体接缝尚未选定或验证。新增任务 1.4 先通过锁定运行时和本地假服务证明其覆盖范围，任务 3.5 再集成并在实际桥资源中复核；这不是已可实施或已安全的声明。如果在既定约束下找不到可证明的接缝，保留拒图保护并报告技术阻塞，不先放行或扩张权限。运行时缺少防护或覆盖无法确认时，应在进入不受保护的 Files／模型副作用路径前失败。

有效防护下，正常原生 Files 上传可继续；原生 adapter 在上传错误后、不产生未授权删除且保持同一调用关联的 inline fallback 也可继续。AWU 不为弥补阻断而另发模型请求、删图或改发纯文本。不能安全继续时返回受控原因：明确未进入原生 handler 的是前置拒绝；已接收后阻断的是运行失败；回执或副作用结果不明则保持 unknown。保留原图片、回执、nativeId 和现有活动保护；已上传文件不因错误、取消或回退而被补偿删除，不以重发探测远端结果。

### 3. 使用固定图片预算和双向有界 JSONL，不做路径式附件兜底

新增共享策略的版本化限额，前端做快速检查，仅在拒绝时反馈触及的限制，不常驻展示格式与限额说明；执行器为最终权威。第一版支持静态 PNG、JPEG、WebP；拒绝 GIF、SVG、动画／多帧和未知格式，不自动压缩或转码。限额为 AWU 资源预算，不冒充供应商的最大能力；路线声明更低限制时取较小值。

| 项目 | 第一版上限 |
| --- | --- |
| 单次模型输入图片数量（含模型专用图片） | 4 张 |
| 单张解码前的实际文件字节 | 4 MiB |
| 单次输入全部图片文件字节 | 8 MiB |
| 单图任一边长 / 总像素 | 8192 / 1600 万像素 |
| 单次输入全部图片像素 | 3200 万像素 |
| 编码后的完整提交请求 | 12 MiB UTF-8 JSON，包含文本和协议开销 |
| Harness 双向完整 JSONL 帧 | 16 MiB，包含 envelope 和换行 |
| 每个 owned 连接的待处理通知／输出字节 | 32 MiB，同时保留既有条数上限 |

校验顺序为：容器和字段类型／数量 → Base64 编码长度预算 → 严格 Base64 解码 → 实际字节预算 → Pillow 格式及尺寸检查 → 受像素预算约束的完整解码 → 实际 MIME 一致性 → 原生块及完整 UTF-8 请求计量。解压炸弹警告作为拒绝；损坏尾部、截断数据、假 MIME 或一张无效图片均使整笔失败。用户提供的 `size/width/height` 不作为可信计量依据。

`file_path` 和普通 URL 仅可作为原有展示元数据，不能在缺少合法字节时触发读取或下载。第一版无需新增受控引用协议；若其他入口已将受控附件解析成合法字节，统一进入同一校验器。

Harness 的 `BridgeWS` 手动入口及排队入口使用严格解析，不能沿用“坏一张跳过一张”的行为；其他 Backend 的现有兼容路径不在本次顺带重构。派发前对最终 `model_images` 和展开后的文本再校验，不能只验证原始可见图片。

配套升级 AWU 传输适配：

- Python 接缝按实际发送的序列化字节计量，并有界读取完整行。通知队列同时计条数和字节，消费后释放预算；不能把 256 条各 16 MiB 当作合理内存上限。
- Node 侧在唯一输入流上添加有界 JSONL 流包装，再交给原生 `JsonRpcLineTransport`；超长且尚无换行的输入也必须终止。输出包装覆盖通知、响应及错误，不能只检查 `params`。
- 不添加第二个 stdin/stdout reader；保留 flush、背压及 owned shutdown。任一帧或累计缓冲超限即明确失败并走归属清理，不截断或悄悄丢掉授权、终态事件。
- 握手核对扩展版本及一致限额后才允许图片提交。现有 WebSocket 50 MiB／Relay 64 MiB 不扩大；同时验证外层 RPC 编码不会使预算内输入越过这两个边界。

12 MiB 请求预算给 8 MiB 图片的 Base64 膨胀留出空间；文本、引用和 envelope 仍按总量检查。原生持久历史事件应携带附件引用而非重复 Base64，但输出限额不依赖这一假设。

**理由与备选：** 保留 1 MiB 会让普通截图频繁失败；无限放大帧会带来内存风险。分片上传及自建临时附件文件协议会增加恢复、路径安全和回收边界，第一版不采用。

### 4. 新增图片发送回执，平台接单不冒充原生接收

为 Harness 图片调用增加版本化的提交／只读状态 RPC 与事件，统一由 BridgeWS 路由和现有 Session 权限检查处理。旧 `sendMessage` 保留给兼容路径；新客户端检测不到目标节点回执能力时保留草稿并明确提示，不降级为无回执的图片发送。旧客户端到新节点仍得到可见失败信息，但不能声称已替它恢复输入框。

每次手动动作生成一次 requestId，同时绑定 userMessageId、assistantMessageId、owner/executor/Session、draft revision 和 Backend/runtime 指纹。RPC 返回的“平台已接单”只表示已登记同一个异步 turn；worker 事件继续报告原生接收。复用已有 chat-turn registry、窗口和更新锁，不等待模型完成才返回 RPC。

| 状态／边界 | 权威证据 | 输入与显示处理 |
| --- | --- | --- |
| 未提交／本地拒绝 | 尚未写出提交请求，或执行器明确前置拒绝 | 原草稿可编辑；显示具体限制 |
| 提交中／平台已接单 | 已登记处理，但尚无原生 receipt | 保留提交快照；不能显示“模型已接收” |
| 已排队 | 队列项及关联回执已落盘 | 沿用既有队列展示，不增加图片状态提示，不显示模型已接收 |
| 原生已接收 | 匹配本 requestId 的 session/prompt receipt | 可清除未被编辑的旧草稿；等待真实运行终态 |
| 失败 | 明确的前置拒绝，或已接收后的运行失败 | 标明失败发生在哪个边界；只有前置拒绝可自动保留原草稿 |
| 结果未知 | 写出后超时、断线或提交持久状态无法核对 | 保留输入与关联，禁止自动重试或入队 |

`chat_turn_started` 和“出现用户气泡”不能用作原生接收证据。`awu/receipt` 从诊断提升为与该请求绑定的结构化事件；`done`、成功的 turn/end、session/wait 以及进程退出仍是不同事实。失败发生在 receipt 前也不自动等于未提交：只有尚未进入原生 handler，或有明确的前置拒绝结果，才能标记 rejected。

在 Session 现有持久范围内增加小型提交记录，保存 requestId、载荷摘要、关联消息／队列 ID、阶段及安全原因，不复制图片。记录先于可能提交的副作用落盘；持久化失败时不得启动提交。同 ID、同摘要只返回原回执；同 ID、不同载荷拒绝，绝不再执行。未知和活动记录不得淘汰；终态记录可压缩，但只要对应消息／队列项仍在就保留去重关联。读状态只查询本机已保存回执和已观测事件，不启动／恢复原生会话，也不通过模型请求探测结果。

前端对一次未知结果最多自动合并一次只读核对；无轮询、无写重试、无节点回退。只读状态接口保留，不在输入区增加手动刷新入口。查不到历史回执不构成“没有提交”的证明。重启时在途记录标为未知，不能自动重放。原生关联中提交前持久 `submitted=True` 的保护保持不变。

输入区不设置独立图片状态栏、能力或限额说明、详情、刷新／恢复按钮，正常添图、接单、排队、原生接收及完成不额外弹出提示。回执订阅仍驱动草稿条件清理；拒绝、失败和未知结果复用既有错误反馈，后续运行错误继续通过聊天错误呈现，不以删除界面为由删除底层校验和幂等保护。

**理由与备选：** 直接将 `sendMessage` 的 Promise resolve 当作成功只证明帧写出；仅监听通用 error 无法区分旧 turn、前置拒绝和部分执行。结构化回执能给草稿提供依据，同时不把这一改动扩展成其他 Backend 的协议迁移。

### 5. 草稿采用身份与修订条件更新，临时授权不进入恢复快照

`ChatInput → ChatPane → useChat → api` 增加明确的发送结果契约，不再用 void 回调代表图片发送成功。提交开始时保存同身份的不可变快照，包括原文字、图片、文本附件及 revision；图片不复制到输入历史、localStorage、日志或回执元数据。只保留当前待决快照及有界恢复槽，不建立无界的 Base64 草稿历史。

输入框在准入期间保留原内容并允许编辑；同 requestId 的重复点击被本地单飞和服务端去重共同挡住。回执到达时：

- 明确前置拒绝且 revision 未变：原文字和缩略图继续保留，提示例如“当前路由不支持图片”或“图片超过 4 MiB”，不说成“缺少 SDK”。
- 原生接收／入队成功且 revision 未变：只清除该快照对应的草稿。
- revision 已改变：不清除、不拼接、不覆盖新草稿；原快照及回执继续按同身份有界保留，不在输入区提供单独恢复入口，也不自动将原稿回填。
- 结果未知：快照与请求关联保留，但不作为可自动发送的队列项；重新发送只能是用户看到重复风险后的新动作，并仍受 Session 活动保护约束。
- 已接收后失败：保留历史消息附件和部分输出，不自动将它复制为待发草稿。

快照及回执按 owner/身份 epoch、executor、Session 隔离，不仅使用 sessionId。切 Session 后只更新原范围；退出账号即清除该身份的内存草稿引用，迟到事件不能写入新账号。组件卸载和重挂不触发发送。对整页刷新，服务端已落盘请求可只读恢复状态及原消息关联；尚未发送的本地图片不新增浏览器永久存储承诺。

`kitApprovalDelegation`、动态工具令牌和本轮独立开关不进入草稿快照、队列或持久回执。原请求的授权仍按现有机制处理；再次提交时需要用户重新独立选择授权，不能复用旧快照里的权限。底层快照恢复守卫仍保留，但不作为输入区产品入口。

**理由与备选：** 发送后立即清空再无条件回填容易覆盖新草稿；持久存储所有图片草稿又扩大隐私和容量范围。因此保留在途原稿并按 revision 清理。按用户最终决定移除额外提示及刷新／恢复入口，必要错误复用现有反馈；不通过新增入口或自动回填打断用户正在编辑的草稿。

### 6. 排队、原生续聊和停止共享既有生命周期

图片入队沿用 SeqTask，增加同 requestId 的回执关联，并让 `handleQueueTask` 返回真实提交结果。严格图片校验在入队前执行；队列项和去重关联必须同一次持久提交后才能返回已排队、推送及 kick scheduler。前端 syncing 项不是成功证据，超时不能删除它再建议直接重发。

入队时不为了验证模型能力启动另一个 worker，不增加额外能力提示，已有能力观察也不授予未来派发资格。正式派发使用当时冻结的 Backend/runtime 和最终模型输入，再执行当前路线准入。拒绝时保留队列项和全部原附件，记录安全原因并沿用失败暂停，不自动跳过、删图派发或改用旧路线。用户之后改队列内容属于新的显式编辑，不能让旧回执覆盖新修订。

原生续聊只通过原 nativeId 恢复历史，提交本轮新增内容块。由原生 attachments 服务恢复旧图引用，AWU 不重建整段可见消息历史、不扫描用户文件寻找丢失图片。恢复失败保留原关联并报错，不创建替代会话。

归属进程清理继续由 owned process tree 负责，不包括远端 Files 清理。取消请求、收到 receipt、完成传输或看到 idle 都不能单独释放未知退出保护；只有现有的归属退出确认允许释放。队列不得在未知退出期间派发，不能结束其他 Session 的进程；失败、停止和进程退出均不授予远端删除权限。

共享 Backend 入口仍执行访问策略、allowed tools、text-only 和 isolated context 校验。明确的纯文本调用携图时拒绝，不因新增图片支持改写其契约；LOOP／辅助调用若本来允许图片，则使用同一个校验器及独立活动身份，不能继承主聊天的临时授权。

**理由与备选：** 入队即承诺未来模型支持会因路线切换失真；把队列失败重新变成自动发送草稿会形成重复请求。因此将入队确认、派发准入和模型终态保留为三个边界。

### 7. 限定错误与可观测信息，不把敏感载荷带入诊断

图片校验和准入错误使用枚举原因、图片序号、实际大小／限额、格式类别和安全建议，不拼接图片字段、Base64、原始 URL、HTTP 正文或 SDK 异常字符串。桥内目录查询也只返回结构化原因，不转发上游错误。

新增 trace 仅记录 requestId、阶段、图片数量／总字节、能力状态及受控路线标识；凭据指纹仅用于内部隔离，不作为用户可见诊断。服务端恶意回显图片或密钥的测试必须覆盖 error、diagnostic、trace 和 RPC error 四个出口。原附件仍留在既有授权消息和原生附件存储，不因脱敏删掉用户内容；不开启原生遥测或新增请求正文日志。

**理由与备选：** 原始异常有助调试但可能携带整个图片请求。只展示稳定错误类别既能解释“为何不能发”，也避免引入旧诊断工程的大范围改造。

### 8. 以锁定原生链路和假服务验收，分开协议证明与视觉效果

验证按边界组织，不以一个 fake Backend 的成功收口：

1. Python 图片策略测试覆盖全部限额的临界值、Unicode／Base64／envelope 开销、损坏与假 MIME、多图中一张无效、路径／URL 不读取、纯图片和模型专用图片计量。
2. AWU 桥及 SDK 契约测试覆盖能力来源缺失、明确 text/image、同名不同端点、环境覆盖、路线／配置修订变化、缺扩展、错限额和最终分派守卫；证实被拒绝时 provider POST 为零，放行时没有递归／双提交。
3. 双向传输测试覆盖 1 MiB 以上的合法图片输入、16 MiB 边界、无换行超长输入、响应／通知、字节队列及背压；所有异常均须确认归属清理或保留未知退出保护。
4. 隔离的锁定 runtime + 本地假目录／模型服务，核对真实请求中的图片可解码、顺序及原始内容正确，而非 URL 文本。覆盖纯图、文字多图、接收后 provider 拒绝、进程退出后续聊，以及续聊只新增本轮输入。若原生 adapter 按其协议转码，比较解码内容与受控变换，不伪称文件哈希必然不变。
5. BridgeWS／队列测试覆盖整笔解析拒绝、落盘前失败、相同 requestId 重复、不同载荷冲突、receipt 丢失、重启未知、队列派发时切换路线，以及停止后不得推进。现有权限、LOOP 和其他 Backend 回归保持通过。
6. 隔离前端测试覆盖慢回执时编辑、Session／executor／账号切换、图片缩略图保留、清理条件、unknown 一次只读核对及独立授权不复用；断言正常流程无额外提示和刷新／恢复控件，实际拒绝或未知仍有错误反馈，且无隐式重发。底层快照恢复守卫由单元测试覆盖，不要求 UI 恢复入口。
7. 原生 Files 矩阵必须包含上传成功、普通错误、quota/storage 错误、同／跨 Session 的 `dsh-` 文件及普通文件、无本地上传记录、历史图片恢复和上传后停止／失败。保留原生无防护风险复现，与受防护链路的验收分开：后者断言服务端收到的未授权 DELETE 为零，安全回退仍包含图片且每次原生模型调用无双提交，接缝缺失／失效则拒绝。不能只用 Files 404→inline 的成功证明安全；unknown、原关联保留和 owned 退出断言不得被预期失败吞掉。

原生测试继续显式 opt-in，只使用临时项目、独立 AWU 数据根和 DSH_HOME、假凭据及本地服务，禁止读取真实用户 Session 或生产收费调用。测试报告分别列出单元、协议、锁定原生和平台结果；未运行的平台／frozen 测试必须写明未验证，不以 source 模式通过替代。

## Risks / Trade-offs

- [部分自定义端点没有明确图片目录元数据，即便实际可能识图也会被拒绝] → 维持 unknown 并说明缺少哪类证据，不提供绕过开关，不把模型名当能力证明。
- [目录声明可能不准确，或模型在接收后仍拒绝图片] → UI 只说声明支持；保留真实失败及附件，不自动重试，不宣称生产视觉效果。
- [原生中间件在分派前改变路线，或 text-only 投影悄悄省略历史图片] → 使用同一 prepared call 分派、身份／修订守卫及带历史图片的负向契约测试；无法保证时不启用图片扩展。
- [rc.3 配额恢复按前缀删除其他 Session 文件，且受信隔离接缝尚未验证] → 远端删除防护作为启用前置，锁定原生契约覆盖实际 Files 分支；无法满足则保持 fail closed，不以方案确认、图片发送或 SDK 默认行为代替授权。
- [阻止自动清理后配额可能持续耗尽，上传后失败也可能留下远端文件] → 只允许已证明安全的原生回退或明确失败，不自动清理、不另发请求补偿；本变更不增加远端清理产品能力。
- [增大帧上限导致内存尖峰] → 单图／总量／像素／完整帧和累计缓冲同时限额；避免回执与 trace 再复制 Base64，解码不阻塞主事件循环。
- [网络断开或进程崩溃发生在原生接收与回执之间] → 持久关联及 unknown 状态优先；只读核对无结论就保持未知，不以“没看到结果”证明未执行。
- [共享发送和排队入口改动引入其他 Backend 回归] → 新协议限于 Harness 图片路径，复用已有注册／权限／队列边界，保留旧协议并跑现有回归。
- [桥资源与 Python／前端版本不一致] → 扩展及限额握手 fail closed；配套资源一致性不过关不得声明图片可用。

## Migration Plan

1. 保留已完成的图片校验与原生基线证据；下一步先验证远端删除防护的安全接缝，再完成能力来源、最终分派、双向传输、回执和前端草稿状态。测试必须先证明锁定 rc.3 能满足这些边界，不能通过 fake-only 成功或仅 Files 404 的回退跳过原生验证；防护未证实前不得解除生产拒图保护。
2. 仅从 `tools/deepseek-harness` 的受信源码重建 AWU 桥；沿用已锁定的上游源码、SDK/runtime、Node 和现有构建脚本，不直接编辑 `build/` 中的生成 bundle。更新图片扩展版本与分发 manifest 校验，验证 source 及已有 frozen 资源入口一致。缺少构建依赖时报告未完成，不在聊天发送时自动下载。
3. 提交记录和消息阶段字段采用可选、向后兼容的版本化结构；历史消息缺字段表示 legacy，不批量猜测接收状态。原生 nativeId、附件存储和历史文件不迁移、不清除，旧失败消息不自动重放。
4. 发布前分别记录 Windows／Linux source 与受支持 frozen 组合的验证情况；本变更实现完成不自动执行发布 Kit 或本机更新。
5. 若需回退，恢复图片 fail-closed 入口并保留已保存消息、图片、回执及原生关联。旧版本不应继续执行新版本留下的在途／unknown 请求；先保留活动保护并由用户核对，不通过回退重发或删除历史。
