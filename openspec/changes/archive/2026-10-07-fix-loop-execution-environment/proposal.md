# Proposal

## Why

“梦幻2026-2”在同一节点、工作区和 Backend 下，自动 LOOP 的原生受限调用出现工具目录拒绝访问、命令不可解析及执行器初始化失败，而人工接管可以调用 OpenSpec；当前系统未核对两条路径的实际执行环境，并把恢复要求留成笼统暂停。需要补齐受限环境中的工具链准备、可验证检查和分类恢复，避免反复空转或误导用户重新安装已存在的 CLI。

## What Changes

- 为自动 LOOP 建立按实际节点、工作区、Backend、传输、原生访问策略及工具链修订隔离的执行环境记录；分别说明宿主发现、原生策略内检查和实际工具调用证据，不能互相冒充。
- 从当前明确选择的工作流及有效命令声明提取最小依赖，优先解析已安装的项目本地 CLI，再使用实际 Backend 的工具路径；向隔离调用传递已核实的执行入口和有界依赖提示，修复宿主可发现、自动调用却无法稳定解析的断层。
- 在支持的原生执行入口中进行只读、有界、无额外模型调用的环境检查，验证实际受限策略下的解析和访问能力；对不能证明等价的执行路径显式标记检查覆盖不足。
- 区分命令未解析、明确入口失效、权限拒绝、原生 runner 初始化失败及协议/探测不支持；提供证据级别、影响范围与具体解除条件，不从模型总结断言“未安装”。
- 将已确认的环境阻塞接入现有暂停/恢复决定；显式重新检查不会启动任务，显式恢复还须核对环境、旧调用退出、成果及原有授权/来源门槛。
- 在 LOOP 面板与流程详情展示自动访问策略及与人工模式的区别，保持紧凑推送、按需详情、无轮询和旧记录未知的兼容语义。
- 不自动安装 CLI、变更系统 PATH/ACL、修复原生沙箱或降级至全权限；真实权限或 runner 故障交由用户/运维处理后再验证。不修改目标 Session 的运行状态，也不把已正常返回但任务受阻的调用改写成模型失败。

## Capabilities

### New Capabilities

- `loop-execution-environment`: 自动 LOOP 的执行身份、工作流依赖与工具入口、受限环境检查、证据分类、恢复检查及轻量可观测性。

### Modified Capabilities

- `loop-continuation-decisions`: 扩展“等待与故障分离且恢复有界”，纳入环境阻塞的证据、暂停、故障计数与显式恢复规则。

## Impact

- 后端：`bridge_ws.py` 的转换/交接、自动调用边界及暂停恢复；`codex_office.py` / `codex_app_server.py` 的有效运行配置和原生检查适配；新增环境协调模块，扩展 `loop_store.py`、`loop_decisions.py` 与有界诊断。
- 依赖声明：复用 `skill_commands.py`、`skill_command_manifest.py`、`skill_command_presets.py` 的有效注册信息，不增加按 Skill 正文执行命令的入口；必要时持久化最小工作流引用，历史授权不进入交接。
- 前端：LOOP 状态类型、执行环境摘要/详情及显式检查入口，沿用 Session/执行节点路由和修订保护。
- 测试与文档：补充受限策略协议契约、Windows/npm shim、环境分类与恢复回归，以及隔离的原生运行器验收记录；更新 LOOP 运维说明。
- 边界：不改变普通聊天/人工接管的权限策略，不改变正式任务来源绑定规则、任务验收或里程碑计分；`taskSource={}` 的本次故障不归因于来源核对器。已知来源刷新错误白名单问题不纳入本变更。
- 本轮仅生成规划工件；实施、上线及真实 Session 恢复分别需要后续操作。
