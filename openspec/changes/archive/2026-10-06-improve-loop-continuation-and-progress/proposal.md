# Proposal

## Why

长任务的单次模型调用可能在完成局部修改、测试和总结后正常结束，而完整目标仍有大量剩余工作。现有 LOOP 已能续跑，但调用终止、任务验收与调度决定尚未统一区分；任务来源主要依赖模型台账，粗粒度父任务也可能掩盖真实增量，造成提前收尾、难以解释的暂停或误判停滞。

## What Changes

- 仅完善自动 LOOP：分别记录调用结果、任务结果与后续调度决定，显示依据、影响范围、下一步及暂停解除条件；正常返回不等于任务验收通过。
- 统一续跑、换路、有限重试、等待、预算/风险停止和成功收口的判断；等待用户不计为 Backend 故障，用户停止和安全/授权边界始终优先。
- 为显式绑定的本节点、本项目 OpenSpec change 增加只读任务来源核对，在轮次边界将 CLI 任务清单与评审证据对账，拒绝遗漏、范围漂移和错误收口。
- 引入父任务下的稳定子里程碑：记录真实实现/验证推进，不提前勾选父任务，不通过重复测试、改名或无限拆分刷新进度。
- 在面板与流程视图分别展示正式任务完成度、子里程碑增量和调度原因；沿用紧凑推送、按需详情与现有节点/Session 隔离。
- 兼容旧记录、旧客户端和非 OpenSpec LOOP；没有新证据的历史信息显示为未知，不倒推暂停原因、不自动绑定或重启旧会话。
- 不改变普通聊天或普通 `/opsx-apply` 的续接行为，不修改第三方 Skill，不自动初始化项目、安装 CLI、归档、发布、提交/推送或扩大运行授权。

## Capabilities

### New Capabilities

- `loop-continuation-decisions`：调用/任务结果分层、可解释调度、有限恢复、暂停与失败分离、持久化及界面一致性。
- `loop-openspec-task-reconciliation`：LOOP 专用 OpenSpec 来源绑定、有界只读快照、真实任务对账、范围变化与不可用处理。
- `loop-milestone-progress`：稳定子里程碑、证据与版本关联、增量去重、回退失效与正式验收分离。

### Modified Capabilities

无。现有主规格只有 `codex-backend-model-catalog`，本变更不修改该能力；既有 LOOP 行为的新增约束由上述三个新规格表达。

## Impact

- 后端：`src/backend/loop_store.py`、`loop_delivery.py`、`bridge_ws.py` 的 LOOP 调度/序列化/RPC；复用 `loop_diagnostics.py` 的真实调用观察。预计新增独立的决策与 OpenSpec 只读适配模块，避免继续堆叠桥接逻辑。
- 前端：`LoopPanel.tsx`、`LoopDeliveryStatus.tsx`、`loopRecordDetail.ts` 及 `api.ts` 的 LOOP 专用类型/方法；增加来源绑定与结构化原因展示，不改变普通聊天表面。
- 数据：在原 LOOP 阶段文件中添加版本化字段和受限快照/里程碑记录；保持现有字段兼容并防止紧凑推送携带完整任务正文。
- 依赖：仅显式启用 OpenSpec 来源核对的 LOOP 需要所选执行环境中已有、支持所需 JSON 协议的 OpenSpec CLI；不新增云服务或自动安装依赖。首版仅支持当前 Session 本节点工作区内项目，外部 store/跨工作区/SSH 文件系统不隐式接入。
- 验证：扩展交付、生命周期、阶段详情与浏览器夹具测试，加入 fake CLI/Backend、来源冲突、恢复幂等和子里程碑反刷进度用例；所有测试隔离于真实用户数据。
- 本次交付仅为规划工件；实现、服务重启、迁移真实会话和发布均不在本次执行范围。
