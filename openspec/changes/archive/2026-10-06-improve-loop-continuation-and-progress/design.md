# Design

## Context

动机见 `proposal.md`。本变更横跨调度、持久化、只读 CLI 边界和两种 LOOP 视图，需要技术设计；不是修改普通 apply 的执行契约。

已核实的实现基线：

- `bridge_ws.py::_loop_run_step` 正常取得非空文本后将步骤设为 `done`；`_loop_do_analysis` 另行评审验收。这是调用与验收的分层，但目前没有统一的显式结果模型。
- `_loop_pause_control` 将暂停写入 `record.error`，`_maybe_autocontinue` 又根据错误记录累计连续整轮失败。新协议需要让暂停不混入故障统计，也不能简单移除 error 后使半完成记录误恢复。
- `_maybe_autocontinue`、`_loop_should_stop`、`_loop_payload` 的 resumable 判断及运行任务注册表共同控制生命周期；不另建第二套独立循环执行器。
- `loop_delivery.py` 已有局部/全局/安全/人工阻塞、完整台账校验和状态高水位进展判断。当前报告来源是模型填写的 `source`，没有直接获取 OpenSpec 任务清单的适配器；没有子里程碑状态。
- `loop_store.py` 的 `effective_max_loops` 当前直接使用用户预算，不再按风险折减；风险阈值仍可独立止损。部分历史说明仍描述旧行为，本次不以旧说明重新引入预算折减。
- `LoopDeliveryStatus.tsx` 显示评审台账和暂停信息，`LoopPanel.tsx` 同时承载面板/流程详情。`loopRecordDetail.ts` 依据修订按需读取详情，紧凑推送不携带完整原文。
- `skill_commands.py` 已有本节点 Backend PATH/项目 CLI 解析及范围预检；OpenSpec 内置入口目前拒绝外部 store。该预检本身不执行 CLI，也不等于下述来源适配器。
- `tests/test_loop_delivery.py` 与 `tests/test_loop_lifecycle.py` 已覆盖局部阻塞、评分不足以收口、历史兼容、失败续跑和有限止损；在其基础上增加新契约，不移除既有约束。
- 本次以 OpenSpec 1.13.1 读取新建 change 的 `instructions apply --json`：任务只有位置性 `id`、`description`、`done`，文件路径在 `contextFiles.tasks`，没有逐项 `sourcePath/line`。实现必须兼容这个实测形状，不能把位置 ID 当作跨轮稳定身份；这只是只读协议观察，不是实现测试通过。

## Goals / Non-Goals

**Goals:**

- 把“发生了什么”“验收了什么”“接下来做什么”变为可以持久化、回放和测试的独立事实。
- 让稳定父任务不变时的有效子项推进被识别，保持原有完整验收与无进展止损。
- 对显式绑定 OpenSpec 的 LOOP 增加真实任务对账，通用 LOOP 不承担 CLI 依赖。
- 首版即覆盖暂停恢复、来源失效、范围变化、重复事件及旧记录迁移，不将这些作为后续隐含缺口。

**Non-Goals:**

- 不改普通聊天的 `max_tokens` 续接、普通 `/opsx-apply`、人工接管的模型调用方式及第三方 Skill 文件。
- 不新增通用工作流引擎、数据库、跨节点文件服务、后台持续扫描或模型自动安装。
- 不将 CLI 勾选、模型评审或证据哈希包装成机器证明；不恢复历史用户数据。
- 不自动绑定历史 LOOP，不把新能力当作 Kit、发布、自动 commit/push 或新的文件访问授权。已由用户单独启用的既有自动提交功能不因本变更增加或削弱权限。

## Decisions

### 1. 在现有生命周期中加入单一决策归约器

新增轻量 `loop_decisions.py`，以类型化事实输入生成决定，不在纯决策函数内调用模型、CLI 或文件写操作。`BridgeWS` 仍拥有运行任务、持久化与调度副作用。

建议新增的版本化概念：

| 记录 | 核心内容 | 来源与权威边界 |
| --- | --- | --- |
| 调用结果 | `normal / error / timeout / cancelled / unknown`、阶段、调用 ID | 来自实际 Backend/异常/调用诊断；模型不能覆盖实际失败 |
| 任务结果 | `partial / implemented / verified / blocked / unknown`、任务/子项及证据引用 | 来自来源对账与评审核实；不是调用成功的别名 |
| 调度决定 | `continue / replan / retry / wait / stop / complete`、原因码、事实引用、影响任务、下一步、解除条件 | 系统综合用户控制、范围、证据与策略生成；模型只有建议权和保守暂停请求权 |

每条决定包含 `decisionId`、`revision`、`round`、`seq`、边界标识、`reasonCode`、`reasonText`、`affectedIds`、`basisRefs`、`resumeCondition`。完成决定另有 `completionScope=automatic|full`，自动范围交接不得投影成所有验收通过。停止细分 `user_stop / budget_exhausted / risk_limit / failure_limit`；等待细分 `auto_off / human_input / safety / authorization / workflow_blocked / source_unavailable / scope_conflict / no_progress / unclassified_pause`。这些枚举不授权执行。

归约顺序：

1. 用户停止、控制权变化、全局/安全/授权硬阻塞优先，保留所有相关事实，不允许后到的模型建议覆盖。
2. 显式绑定来源无效、范围未核对时，不允许依赖其继续自动写入或成功收口；CLI 的 `blocked` 与读取失败分开。
3. 核对完整验收；达到现有分数与必要独立复核要求才允许成功收口。仅有明确人工剩余项时使用“自动范围完成，待人工核验”的交接结果，保留正式未完成项。
4. 若仍未完成，则应用预算/风险/连续真实故障止损；不得为获取下一轮而重置计数。
5. Auto 关闭则等待用户。允许的故障可有限重试；无进展要求换路并在耐心耗尽时暂停；其余选择就绪任务继续。

成功验收若恰好在最后一轮发生，可以如实收口；预算只是禁止再启动新工作，不否定已取得的有效完成证据。没有就绪任务且没有可说明的解除路径时，报告待核对/需输入，不编造下一步。

选择此方案而非仅加一段“继续直到完成”的提示词，是因为普通结束文本不能可靠控制外层生命周期；也不采用额外模型专门判断是否续跑，避免增加每轮固定成本与自述循环。

### 2. 暂停独立终结，恢复复用成果但不盲目续写

为新记录增加独立的终结种类和恢复依据。`record.error` 保留真实异常及兼容旧记录，不再用来承载新式人工等待。相应更新 `_loop_payload`、resume-or-new、风险计算和连续故障统计，防止“error 清空后把 paused 当 resumable”的回归。

- 暂停终结本次自动调度，保留已完成步骤/产物与调用身份，不要求伪造分析分数。
- 用户显式恢复时先检查权威任务注册表、调用退出状态、控制权、来源与解除条件。终结的暂停轮次不从中间盲续，下一次 prepare 带入已有证据重新编排；真正可恢复的中断仍遵循现有断点语义。
- 旧调用退出未确认时禁止新的写调用；取消不承诺已撤销运行中工具的副作用。
- 以边界身份与修订去重，在同一 Session 的生命周期控制中先保存决定再由原 `_schedule_loop_iteration` 调度。重复事件不得重复开轮；用户暂停与调度竞态时再次核对控制权。
- 进程重启不自动执行遗留的“继续”决定，只恢复状态并允许用户显式恢复。重复显示、重连或旧决定读取均无调度副作用。

不承诺跨崩溃的工具“恰好执行一次”；使用产物复核、边界去重和单一运行任务避免常规重复，崩溃后由明确恢复重建当前事实。

### 3. OpenSpec 来源是可选绑定，不是隐式检测

在 LOOP 的任务台账区域增加“任务来源”入口，经现有 session-routed RPC 显式发现/绑定。绑定可在创建后但未开始执行时，或空闲且没有 resumable 记录时变更；运行中展示只读状态。操作不会启动 Auto 或下一轮。

绑定身份包含执行节点、Session 工作区规范路径、当前实际 execute Backend 配置身份与非敏感修订、CLI 解析结果/版本、OpenSpec root 和 change ID。规划/评审可用其他模型，但共享同一执行来源。执行环境配置变化令缓存失效，先重新核对；不得静默转用另一个节点或 Backend 的 CLI。

首版仅支持当前 Session 节点上工作区内部的项目。先检查路径、父项目和显式 store 配置，再执行只读发现；返回 root 与 changeRoot 必须仍在认可范围。外部 store、全局 defaultStore 导出的外部根、SSH 执行文件系统以及符号链接/reparse point 导致的越界明确报不支持。通过 AWU Relay 访问该 Session 的真实执行节点仍受原路由支持，不新增跨节点回退。

通用模式保持默认；即使只发现一个 change，也只预选展示，必须经用户确认绑定。用户改绑/解除绑定是范围变化，不是忽略未完成任务的快捷方式：留存原范围和未解决问题，建立新的比较基线，不从修改历史中制造完成证据。

替代方案是从目标正文或最近 Skill 命令自动推断绑定，但历史摘要可能截断、跨 change、缺少授权，因此不采用。

### 4. 有界只读 CLI 适配器与稳定任务快照

新增 `loop_task_source.py`，独立于模型调用，复用或抽取现有 CLI 路径解析思路但不更改普通 Skill 命令行为。只允许预定义的版本/帮助、`context`、`list`、`status --change`、`instructions apply --change --json` 查询；后者只是读取任务及动态状态，不执行 apply。

使用本节点当前 execute Backend 环境解析 CLI，优先受信工作区的 `node_modules/.bin`，再使用该环境 PATH。命令使用校验后的参数列表，不执行任务正文或 CLI 返回的指令文本；Windows `.cmd` 包装使用项目已验证的启动方式及严格参数校验，不引入动态 shell 拼串或自动 `npx` 下载。

适配协议读取实际 CLI 版本与所需 JSON 字段，而非仅凭版本号猜格式：根与 change 路径、schema、任务描述/完成标记、任务文件定位、ready/blocked/all_done 和缺失工件等事实。首版覆盖两种可验证形状：

- 提供逐项 `sourcePath/line` 的协议：校验真实 checkbox 与描述/状态，使用源任务中的显式稳定编号，不假定名为 `id` 的字段天然稳定。
- 本机 1.13.1 的简化协议：只读 `contextFiles.tasks` 所列范围内文件，在有界 Markdown checkbox 解析结果与 CLI 的完整描述/完成标记逐项唯一一致时，提取源任务显式编号（例如 `1.1`），补足路径与行号；CLI 的 `1`、`2` 等序号仅作为本快照内的定位，绝不跨轮比较。支持正确识别代码围栏、checkbox 标记及空白的已验证语法；多文件歧义、重复源编号、描述不一致或无显式稳定编号均报告不能可靠映射。

只读 Markdown 映射是核对已成功取得的 CLI 结果，不是 CLI 失败后的宽松替代解析；协议不支持时给出具体原因，不从错误文本“捞”完成任务数。两种形状都须经过夹具/隔离契约验证。

初始有界配置（实现常量，可在保持显式溢出行为下调优）：单进程 20 秒、一个快照流程总计 60 秒、最多一次瞬态重试、stdout/stderr 各最多 1 MiB、最多 100 个正式任务。超时/错误必须关闭并确认查询进程退出。解析、协议和路径错误不盲目重试。诊断只保存脱敏类别、退出码和必要结果，不保存环境变量、令牌或无关 CLI 原文。

快照保存 binding/revision、采集时间、CLI 状态、任务映射和文件指纹。分别计算：

- `scopeDigest`：稳定身份、任务含义、正式验收输入及关联，不含勾选位和行号；有限规范化仅处理换行、缩进、空白等，不自动判定语义改写等价。
- `stateDigest`：任务勾选状态和定位信息。
- `artifactDigests`：本 change 的规格/设计/任务等验收依据；通过 CLI 返回的工件路径、受限读取校验，不递归扫描整个仓库。

原文件字节指纹变化只表示缓存需要刷新，不直接表示范围变化；任务勾选、行号和纯排版变化经规范化核对后不得触发人工范围确认。只有验收含义变化或无法可靠映射时才进入范围冲突处理。

任务没有可靠 ID、ID 重复或路径不在范围时，不创造行号伪稳定 ID。更换 ID/语义变更保留差异并要求核对，不用模糊匹配静默接受。

采集时机为绑定确认、prepare 前、execute 后进入 analysis 前，以及显式恢复/范围确认；同一边界请求合并。每轮最多存前后两个必要快照，全文在记录详情中；不按 token delta、计时器或界面展开轮询。异步结果必须匹配节点/Session/binding revision/边界才能采纳。

### 5. 对账是独立验收条件，不能替代评审

新增纯函数 reconciliation，把正式快照与模型 `delivery` 对照，产出遗漏、额外项、状态冲突、来源变化及所需处理。正式任务集合由来源决定，模型不能删项减分母；依赖和业务验收仍来自规划/评审证据，CLI 没有提供时不伪造为权威依赖。

- 未勾选的非人工正式任务不能成功收口；已实现但遗漏勾选时由执行阶段遵循原 Skill 核实后修正，适配器绝不写 tasks.md。
- 全部勾选并不证明实现，`all_done` 不覆盖证据缺失、范围漂移、Addon、真实阻塞与独立评审门槛。
- 明确人工项不从总数删除，也不强行勾选；显示自动范围已完成与人工待验分离。
- CLI `blocked` 是工作流阻塞；CLI 不可读是来源不可核对。后者保留旧快照并标过期，在有界重试后暂停该绑定的自动写入与成功收口，不能自动解绑降级通用模式。
- 仅排版、行号和勾选变化更新快照；新增、删除、改义、重编号或验收工件变化形成差异。明确新用户 Addon 可作为范围处置依据，但仍须核对新清单；否则空闲时由用户确认范围修订。
- analysis 后及下一次写调用前验证快照依据是否变化；变化则刷新只读快照并重新判断，不用旧快照放行。此检查不是文件锁，外部并发修改仍是需披露的限制。

不把本地读取失败升级为所有无关 Session 的全局阻塞，也不允许在已绑定工作流内部以“独立任务”为名绕过来源不可核对。

### 6. 子里程碑作为有界侧台账，不修改正式任务结构

在 `loop_delivery.py` 的规范化、进展比较及 `LoopRecord` 上增加版本 2 子里程碑协议。父任务继续使用正式来源或通用台账的稳定 ID，不把子项塞入父任务 items 分母。

子项字段包括 `id`、`parentId`、`scopeRevision`、`originRef`、`acceptance`、`acceptanceDigest`、`status`、`registeredSeq`、`evidenceRefs`、`baseline`、`validity`。上限先定为每个父任务 20 个、全范围 200 个子项，超限明确不完整而非静默裁剪通过。

规划可在 prepare 登记子项，校验父任务与原验收条件的引用后冻结进本轮计划；已有任务边界已足够细时不强制再拆。执行仅报告产物与测试结果，评审核对条件映射和证据后采纳推进。默认独立评审保持独立；用户关闭该策略时，界面不能仍称独立核实。

进展规则：

- 首次有效清点建立基线，优先在 prepare 的执行前快照中冻结。该基线之后本轮真正完成的已登记子项可以计为新进展；只有到执行后才发现且没有执行前依据的已有成果作为基线，不计本轮新实现。缺少可比较旧基线不倒推为停滞。
- 对执行前已登记、范围内且有效的子项，首次 `pending → implemented → verified` 的证据推进可重置停滞计数；父任务可继续 pending。
- 对 `(父任务身份, 验收条件身份)` 保留已达到的高水位及已记账转换，重复通知、标题改名或新增别名不重复计数。
- 新 ID 同义条件和没有交付意义的动作由规范化与评审去重/拒绝。系统可机械核验身份、引用和重复，但不能宣称完全识别自然语言等价；无法确认时标待核对，不给信用。
- 不允许通过每轮追加细碎动作逃避停滞；新增子项须有原需求条件映射和独立可验收结果。数量、字符、工具/提交/截图数不是计量。
- 当前状态与历史高水位分开：回归、环境或相关产物变化使证据失效，收口读取当前有效状态。恢复到同一历史高水位如实记录修复，但不反复算首次推进；相关长修复仍受预算与耐心限制。

证据复用按影响范围而非整个 Git HEAD 判断。记录产物相对路径/指纹、验证命令与结果/环境及引用；有界核验仅访问授权工作区证据，不触碰真实用户目录或执行证据中的任意命令。自动核对只能证明文件身份/结果来源，正确性仍需评审。无关文件修改不使所有证据失效，依赖不明则定向复查。

拒绝“模型自报百分比”或自动把子项总数转成父任务完成比例，因为它会鼓励拆任务刷进度并掩盖集成验收。

### 7. UI、RPC 与存储保持兼容

新增 LOOP 专用来源发现/绑定/范围确认方法，通过 `BridgeWS` 和 `frontend/src/api.ts` 原有身份路由，禁止直接 UI 读服务器路径。绑定与范围确认带期望修订，运行中或过期请求明确拒绝；来源发现只由显式操作触发。

`LoopPanel` 的任务来源卡展示未绑定、已核对、过期、冲突、不可用与核对时间；决定卡展示下一步及解除条件。`LoopDeliveryStatus` 展示正式任务数、子项实现/验证数、本轮认可增量、人工剩余项和失效证据，两种视图使用相同派生数据。

保留既有 `stopReason`、`progressGuard`、步骤状态作为兼容投影，新字段版本化；`done` 明确标为调用/步骤结束而非业务验收。新客户端以新协议为准，旧客户端不能清空其不认识的状态。旧 paused 文本不被猜测为精确新原因或倒改历史故障；新失败计数从新的明确结果基线计算，旧风险/轮次预算不被重置。

紧凑 payload 仅带决定摘要、来源状态/计数/修订、子项计数；完整快照、证据和子项列表通过 `loopGetRecord` 或明确的来源详情按需读取。`loopRecordDetail` 修订纳入新数据版本，原有 coalescing/过期响应保护和隐藏视图不请求的规则保持不变。单条决定原因限制 1200 字符、引用/任务 ID 列表限制在已支持任务容量内；运行诊断不复制凭据或整段上下文。

### 8. 验证分层及样例回放

使用 fake Backend 和 fake OpenSpec 可执行夹具，验证真正 argv、cwd、环境来源、退出码、超时、路径及 JSON 边界。Windows CLI 包装使用隔离小进程测试；真实安装 CLI 仅在临时项目/用户目录执行只读协议契约，不在产品工作区跑实现或付费模型。

纯函数测试覆盖所有决策优先级、正式任务对账、身份去重及里程碑高水位/失效。生命周期测试覆盖暂停与故障分离、重复通知、恢复重新核对、旧调用退出未确认、重启残留与范围确认竞态。

核心样例夹具固定 25 项任务，其中 2 项正式完成：第一轮确认外壳子项推进但父任务未完，下一轮选择属性/技能就绪工作；重复提交相同外壳证据不再计进展。整个样例不得依赖真实游戏项目、截图结论或历史用户文件。

前端沿用 `frontend/tests/acceptance/loop-stage-details.spec.ts` 与 home 单测体系，覆盖桌面/窄屏面板和流程、绑定/冲突/解除入口、晚到响应、详情刷新次数、旧字段兼容。普通聊天与人工接管作为负向回归：不增加自动调用或 OpenSpec 查询。

## Risks / Trade-offs

- [评审仍会误判自然语言条件或证据] → 显示评审来源与局限；仅确定性校验能机械验证的部分；未知不收口，提供人工可追溯依据。
- [新增 CLI 依赖造成额外等待] → 仅显式绑定启用，边界查询、合并请求与硬上限；不可用时明确暂停，不无限轮询或自动安装。
- [严格快照校验使外部修改更容易触发暂停] → 排版/勾选与语义变更分开，展示差异；用户可明确确认新修订，不静默放行。
- [新增子项使模型绕过无进展门槛] → 执行前登记、原条件映射、基线规则、去重高水位和容量上限；重复活动不计分。
- [真实回归修复长期没有新的高水位] → 展示修复事实但保留保守暂停，沿用用户可调耐心值；不制造假任务或自动增大预算。
- [暂停类型迁移误触发 resume 或旧客户端覆盖] → additive 版本字段、单一决策入口、权威运行注册表、旧省略字段保留和专项生命周期测试。
- [新增快照使 LOOP 加载膨胀] → 有界正文仅放详情，紧凑推送计数化，无后台轮询，验证 payload 与详情请求次数。
- [其他开发同时修改 LOOP/UI 文件] → 实现前复核现有工作树并保留无关改动；本次规划不宣称清理或覆盖这些修改。

## Migration Plan

1. 先以添加字段方式落地版本化协议、纯函数及兼容测试，再接入原调度边界；不扫描或批量改写所有旧 LOOP 文件。
2. 新记录写新协议；旧记录保留未知与原文，只在用户显式运行后的新边界产生新事实。自定义策略、Auto、预算及历史事故不自动清除。
3. 来源绑定默认无，里程碑默认空。只有用户确认来源后开启适配；旧非 OpenSpec LOOP 继续运行。
4. 通过后端、前端和隔离端到端回归后，由用户另行安排服务更新/重启。实现阶段不得以验证为由重启当前生产服务或迁移真实运行中会话。
5. 回退优先停用新入口并保留添加字段和历史；若必须回退到不识别新验收门槛的旧二进制，应先显式暂停相关 Auto、备份阶段文件并告知用户旧版本不具备新保护，不能静默降级续跑。
