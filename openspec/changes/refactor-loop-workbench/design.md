# Design

## Context

动机见 `proposal.md`。本设计基于 2026-10-10 工作树的静态代码和现有测试检查，尚未进行新界面的运行或视觉验收。

- `LoopPanel.tsx` 约 2160 行，同时持有状态请求、详情缓存、流式文本、目标编辑、动作和多种展示。顶层先渲染阶段轨道，再排列进展、环境、来源和调度提示，随后才进入实际工作区域。
- `viewMode=panel|flow` 分叉使面板拥有目标/补充/运行操作，流程拥有泳道；流程空状态甚至要求用户切回面板开始执行。两处重复渲染指标和接管相关入口。
- `MetricBar` 根据 `bestScore >= 70/85` 直接生成“可交付/可输出”，与现有 `loop-continuation-decisions` 的完整验收语义不一致，应删除这一展示推导。
- `LoopSourceCard` 将发现、核对、处置输入和解除绑定铺在日常页面；`LoopEnvironmentCard` 常驻未知环境、工作流依赖和说明。这些能力本身有价值，问题是频率与视觉层级相同。
- 已有 `loopRecordDetail` 的修订与懒加载、`useLoopControl` 的共享回执、任务阻塞详情、调用诊断和身份隔离可复用。测试 `loop-stage-details.spec.ts` 与 `loop-control-handoff.spec.ts` 已覆盖模拟 RPC、迟到结果、读取次数和工程活动门槛。
- `add-session-engine-workbench` 仍在进行；Chat/Engine 与人工控制的语义不得被新 LOOP 布局取代。`fix-loop-scoped-blocker-recovery` 的已实现状态作为输入兼容，不修改其工件。

## Goals / Non-Goals

**Goals:**

- 将“现在做什么、做到哪里、需要我做什么”放在一屏主层，并给出完整的旧入口去向。
- 用纯展示投影和单一动作适配层降低组件复杂度，保留权威状态与按需取证。
- 让首屏减法、操作边界和读取次数都可被夹具验证。

**Non-Goals:**

- 不增加前端调度器，不重新计算后端控制权、阻塞解除、验收结论或模型风险。
- 不把主组件拆成几个同样堆叠的文件就视为完成；不新增平行的“新版/旧版”长期入口。
- 不清理阶段文件、用户记录或工作区产物，不改变真实停止/丢弃/回滚 API。

## Decisions

### 1. 采用一个主工作面和一个按需详情面

默认布局自上而下：

1. 紧凑身份栏：目标标题/展开全文、阶段中文名、轮次、Auto 状态；沿用 Session 现有 Token 与 Chat/Engine 入口，避免重复顶栏。
2. 统一动作区：一个主要动作、Auto 控制、必要的停止入口，以及次级人工接管/设置/更多操作。
3. 当前工作区：最新已知阶段/步骤、短进展、已知成果与剩余缺口；真正受阻时出现一个“需要处理”区域。
4. 补充入口：待纳入数量与轻量输入入口，明确“后续规划纳入”；历史与目标版本从对应入口查看。
5. 详情导航：“过程与历史”“成果与证据”；任务设置另开同一个详情容器，不再新增主视图切换。

宽屏详情在右侧；空间不足时用可关闭的全宽详情页/抽屉，保留当前状态和返回位置。过程图沿用可点击阶段/步骤，但不承担另一套运行控制。只在用户展开历史时呈现全部轮次；默认关注当前轮，用户主动选中的历史不会被流式更新抢走。

选择这一结构，是因为用户任务有稳定的主线，而诊断与配置是低频支线。只给现有卡片增加折叠按钮，仍会留下过多平级标题和两套操作路径，因此不采用。

### 2. 删除与迁移清单是交付的一部分

| 当前内容 | 新去向或删除方式 |
| --- | --- |
| 顶层面板/流程切换及两套大分支 | 删除；统一工作台，过程作为详情目标 |
| 原始 `loopidea/loopexecute/loopout` 英文轨道 | 删除；中文阶段状态与当前步骤取代 |
| 最佳分数、最近分数、风险大卡及分数成功徽标 | 删除主层组件；数值移至评审诊断，成功徽标只消费可信验收结论 |
| 重复人工接管按钮和重复不可用说明 | 汇入 Session 共享控制入口；工作台引用同一状态，独立浮层复用同一组件 |
| 环境、来源、停滞、调度多个同因横幅 | 转为问题投影，按稳定问题身份归并，按需看原始依据 |
| 未绑定的来源卡、正常环境大卡 | 从默认主面移除；任务设置可发现，异常时提升 |
| 原始来源 JSON、调用耗时、Backend 分档和长策略说明 | 任务设置/诊断详情，默认不加载大正文 |
| 分数环式轮次卡和重复全量时间线 | 统一轮次选择与过程导航；不再同屏展示两套轮次列表 |
| 目标原文、演变、原始想法、Addon 历史 | 保留，分属目标/补充详情，不与运行操作抢占首屏 |
| 常驻“不是完成证明”等通用教学文字 | 移至帮助/相关详情；真实异常保留具体解释 |

移除不再引用的样式、props、状态和测试选择器；不删除原始数据。全局“俺寻思”保持唯一入口，不重新加回 LOOP。

### 3. 用状态操作表明确按钮语义

| 已知状态 | 主动作 | 保留的相关操作与边界 |
| --- | --- | --- |
| 目标准备 | 确认目标 | 想法展开、整理目标、任务设置；确认目标不擅自新增加一条自动执行路径 |
| 空闲且可运行 | 运行下一次 | 单独选择 Auto；人工接管按既有资格核验 |
| 有真实断点 | 继续未完成步骤 | 必须保留断点身份；丢弃在更多操作中 |
| 正在执行 | 进行中状态 | “停止后续自动执行”仅关闭 Auto；“停止本轮并查看结果”使用现有停止并转结果语义，提交后等待真实终态 |
| 需要用户/来源/环境处理 | 处理当前问题 | 可查看全部问题；检查/确认不隐式运行，运行入口直到条件满足才开放 |
| 控制权转交或退出未确认 | 核对当前状态 | 保留共享请求身份和状态反馈，禁止相反或重复转交 |
| 本轮结果 | 开启新一轮 | 明示现有 Auto 是否会连跑；未完成、自动范围完成及完整验收分别表达 |
| 人工接管只读总览 | 返回人工工作区 | 查历史/证据；不在总览触发 LOOP 写操作或停止工程活动 |

“一个主要动作”限制视觉主次，不强行把停止、Auto 和接管合并成万能按钮。危险的 `loopDiscard` 保持单独确认，清楚列出记录、补充和上下文影响；可选磁盘恢复继续第二次明确选择，不改成普通停止。

### 4. 纯展示投影与共享控制权保持分离

建议将 `LoopPanel` 保留为兼容容器，抽出 `useLoopWorkbenchState`（轻量状态/流/详情缓存）、`loopWorkbenchView`（纯投影）和 `LoopWorkbench`（布局），再按职责分为当前工作、问题列表、动作区和详情容器。`LoopPolicyEditor` 仍为新建会话及设置共用，不复制配置模型。

投影输入是现有 LoopState、最新有效控制回执和已加载详情；输出为阶段文案、当前记录、进展摘要、问题和动作可用性。问题保存 `kind + sourceId + revision + affectedIds` 与详情目标；只有可靠关联才归并，同样文案不自动判为同一问题。

展示优先级先考虑控制权未确认/未退出和安全授权，再考虑来源/环境、用户输入、局部阻塞与停滞，但这个排序只用于显示，不能重新决定哪些独立任务可以运行。旧字段未知就显示未知。必要的摘要缺失时在 `_loop_payload` 增加向后兼容的有界计数/引用，不在前端扫描完整阶段正文制造“已完成”。

现有 `useLoopControl`、控制状态和 `LoopEngineeringActivities` 保持唯一语义来源。关闭详情、切换 Chat/Engine 和隐藏组件只影响展示，不取消控制回执、不释放 reservation、不重发写请求。

### 5. 将 OpenSpec 来源和环境放到同一任务设置中的两个独立部分

设置按“任务来源”“执行配置”“诊断”组织。来源负责 change 和正式范围；执行配置负责 Backend、策略和工作流依赖。这两者可以相邻呈现，但不能互相暗含授权或绑定。

用户可以仅绑定来源、仅选择依赖，也可以完全不使用 OpenSpec。发现后仍需明确确认候选；绑定不是运行，重新检查环境也不是恢复。发生来源冲突时，问题入口直达差异和处置输入；正常状态不把解除绑定输入框铺在主面。

保留执行端限制，不为了少一个点击把 bind、check、run 合并成一次隐式动作。主规格的来源/环境展示条款在本 change 中更新；其余查询、范围、授权和有界检查条款完全保留。

### 6. 验收采用状态夹具、操作计数和屏幕证据

- 布局夹具：目标准备、空闲、运行、断点、单/多问题、结果未完成、待人工、人工只读、离线/旧执行端。
- 主层验收：1366×768 和 390×844，在目标摘要上限内不滚动主页面即可辨认目标、状态与主要动作；只有一个问题容器，无大指标、未绑定来源卡和重复接管入口。
- 功能验收：流程节点、阶段审计、已完成步骤、补充纳入说明、目标历史、来源变更、环境检查、转交超时/水合失败全部可达；对多轮历史选择不强制跳转。
- 性能验收：打开通用 LOOP 不调用来源发现/环境检查；隐藏详情和重复 push 不增加详情读取；同一可见修订合并读取；大历史只传摘要，沿用既有有界协议。
- 语义验收：高分但缺证据、2/25 正式任务与子项推进、调用正常但任务受阻、预算结束不称成功。
- 复用 Playwright 路由夹具与假 Backend，测试用户数据目录隔离；禁止以生产 Session 或真实付费调用充当夹具。视觉截屏和键盘实际操作属于 apply 阶段验收，不用本规划校验冒充。

## Risks / Trade-offs

- [隐藏配置后不易发现] → 保留固定“任务设置”入口，异常直接定位对应操作，不依赖多级菜单寻找阻塞。
- [把多个错误合并后漏掉门槛] → 问题列表保留身份和数量，仅合并可靠同源事实，覆盖多问题夹具。
- [显示简化掩盖执行复杂度] → 主层用真实状态与具体下一步，详情保留原文、证据及不确定性，不使用模型改写作为唯一状态。
- [与在途 Engine 变更冲突] → apply 前检查相关工作树，只调整布局连接，不改控制协议、工程活动核验或已有 change。
- [中文阶段名让熟悉旧名的用户难找] → 过程详情保留可查的原阶段标识，不在首屏继续双重展示。

## Migration Plan

1. 先冻结上述状态/行为夹具和入口迁移清单，再替换布局，复用原 RPC 与状态存储。
2. 完成语义回归后移除旧分支，而非用长期 feature flag 保留双份交互；现有历史记录不迁移、不重写。
3. 更新 LOOP 文档和实际实现对应的 AGENTS 说明，记录入口变化及仍适用的执行保护。
4. 前端回退恢复上一版包即可；若加入摘要字段，旧客户端忽略它们，回退不清理阶段数据或启用 Auto。不在此次规划中部署、打包或重启生产端。
