# Design

## Context

动机与范围见 `proposal.md`。本设计基于 2026-10-10 当前提交 `1800ae4` 的源码、测试和规格；旧交互参照 `26f3201`。以下是已观察事实，不是对截图中生产 Session 根因的推断：

- `LoopPanel` 已抽离 `useLoopWorkbenchState`，后者拥有按身份隔离的订阅、流缓冲和修订合并详情缓存；这些是保留项。
- `LoopWorkbench` 将过程与配置共用详情分类，宽屏详情固定占 56%；原 `StageRail`、`MetricBar` 和分数环式轮次导航被删除，现有 `LoopFlowView` 尚可复用。
- `loopWorkbenchView` 把 `latest.status=unsupported/stale` 与真实 blockers 同列为 priority 10；主动作在 priority < 50 时变为问题入口，`LoopPanel` 又在 priority < 30 时禁用恢复。纯数据复现确认：空 blocker + unsupported 会禁用恢复，而正常摘要不会。
- `_loop_environment_record` 仅将 blocked 检查加入 blockers；`probe_gate` 不因 unsupported 本身暂停无既有阻塞的调用。实际运行还在 `_run_loop_iteration`、来源/控制权及各调用边界核验，因此 UI 严重程度不是资格来源。
- `_loop_environment_dependencies` 在来源已绑定时返回 OpenSpec 依赖，而 `LoopEnvironmentCard` 只显示 `workflowRef.command`，会把没有额外选择误写为“未选择”。
- `LoopSourceCard` 对所有已绑定状态展示处置输入和解除绑定；问题入口只传递 settings/evidence 分类，不携带具体处理对象。
- 旧 `MetricBar` 用 `bestScore >= 70/85` 直接贴成功徽标；恢复视觉不能恢复该判断。
- `refactor-loop-workbench` 已实现但未同步/归档；其新能力 `loop-workbench-experience` 目前不存在于主规格。已有 `loop-milestone-progress` 仍要求面板/流程一致，沿用该能力补充恢复评分时的进度分离，不另建类似能力。

## Goals / Non-Goals

**Goals:**

- 恢复用户熟悉的过程可视化与直接操作，复用新状态基础设施，不复制两套控制器。
- 将来源管理、诊断和问题处理拆成明确任务，减少概念与导航负担，而非只把旧卡片移入弹层。
- 用执行端事实表达“可请求动作”，消除诊断显示误锁，同时保留所有实际执行门槛。
- 通过视觉证据、操作计数和边界夹具验收恢复效果及无副作用行为。

**Non-Goals:**

- 不改评分算法、Auto 调度、任务阻塞复核、用户数据测试隔离、授权或进程退出确认规则。
- 不迁移/删除 Session 或阶段记录，不启动真实 Godot、读取被拒的真实存档、改 ACL 或切换节点代执行。
- 不恢复已移出的全局“俺寻思”重复入口，不改 Chat/Engine 模式与 Session 导航，不新增自由聊天框。
- 不整包 Git 回滚、不新增 UI 框架、不在此变更中发布、重启、自动同步或归档其他变更。

## Decisions

### 1. 恢复两种主视图，保留一个状态与动作层

`LoopPanel` 继续作为外壳；`useLoopWorkbenchState`、共享控制权 hook 和动作防重入口保持唯一。恢复的 viewMode 只决定渲染布局，不决定调度、订阅或缓存归属。新 Session 默认面板，已打开 Session 在本地按用户/节点/Session 保留选择；无服务端记录迁移，不能借切换视图清空草稿或控制回执。

布局顺序：

1. 紧凑标题与“面板 / 流程”切换，三阶段轨道保留原标识并配中文解释；它是阶段指示，不是跳过步骤的操作。
2. 同一稳定控制区：运行下一次/恢复指定 Loop、Auto、停止本轮、人工接管；目标与策略有直接入口。丢弃/文件恢复仍在危险操作中独立确认。
3. 最近/最佳评分、风险、本轮预算及紧凑正式任务摘要；评分说明一次标明范围，不在每个指标后堆“不是验收”长提示。
4. 主视图：面板显示目标、Addon、轮次卡与分数环及所选记录；流程显示宽度完整的 Prepare/Execute/Analysis 泳道与分步输出。两个视图均可运行、补充和调整策略，不要求来回切换才能操作。
5. 有实际问题时在控制区附近显示一条紧凑提示，非阻塞诊断不占用该位置。

原主题变量、边框、圆角、状态色和节点动效为视觉基准。空数据明确未评审；动画和计时只属于当前轮最后一个有效活动记录。评分不覆盖验收，历史最高分的范围以实际后端字段含义标注，不擅自重算分数。

替代方案：整文件恢复旧 `LoopPanel` 会丢失懒加载和控制权修复；只保留现布局再加折叠开关无法恢复主流程体验。均不采用。

### 2. 辅助面按操作对象打开，不再有万能“任务设置”仓库

| 入口 | 默认内容 | 展开或操作时才出现 |
| --- | --- | --- |
| 来源摘要 | change、核对状态、正式任务勾选 | 来源详情、最近核对、选择/更换来源 |
| 策略与心智 | 原策略摘要和直接编辑入口 | 既有策略编辑器、Backend/模型分档 |
| 运行诊断 | 有无已知运行阻塞、检查覆盖说明 | Backend/角色/策略/版本、证据、额外工作流依赖选择 |
| 具体问题 | 原因、影响范围和动作 | 指定修订的差异确认、检查记录或受阻任务 |

用带身份的目标替代仅有分类的 section，例如问题 ID、来源修订、检查 ID、轮次及受影响任务。打开“核对范围差异”直接到该表单；打开“查看受阻任务”直接到相应台账。只读来源详情不常驻解绑输入；用户先选“解除绑定”，才展示影响、处置依据和确认。没有冲突时不展示空差异列表。

正常页面不默认分配辅助栏宽度。需要操作时复用统一辅助容器：桌面为有宽度上限的按需浮层，窄屏为全宽操作面；只有一个标题和关闭/返回，不加重复“详情/任务设置”分类。阶段输出仍在对应主视图内展开，不迁到此配置浮层。Escape、焦点返回、失效对象和草稿保存按统一规则处理。

替代方案：直接把三张旧卡搬进新的弹框只改变位置，不消除解绑、依赖选择和正常查看的混淆，因此需要拆分卡内操作状态。

### 3. 问题显示与运行资格分离，执行端保有权威

前端问题投影输出 `severity / effect / affectedIds / evidenceRefs / target` 等展示数据，排序仅影响提示顺序；删除 `priority < N` 决定运行/恢复可用性的耦合。

在现有紧凑状态增加版本化、有界的动作摘要，覆盖运行/恢复及其明确禁用原因。字段采用“可请求”含义，例如 `canRequest`、动作类型、原因码、依据引用及当前 round/seq/修订，不命名为“ready/已就绪”。复用执行端现有无副作用资格与门槛判断，不在推送中跑 CLI、解析完整任务文件或进行模型请求，不另建前端调度器。动作提交仍经过原 RPC 和实际调用前置；摘要是当时快照，不是授权令牌。

已知源冲突、适用环境故障、未确认退出等显示对应处理入口；修复/重新核对与恢复是两个动作。某类暂停原本允许显式恢复后再核验的，继续保留该路径，不因摘要新增限制或自动解除条件。Auto 关闭只说明未自动续跑；预算和风险不因手动按钮或新视图而被提高。局部阻塞是否有独立工作由既有任务复核结果决定，不从 issue 数量判断。

| 条件 | 提示 | 动作语义 |
| --- | --- | --- |
| unsupported/部分覆盖，无 blockers，无其他门槛 | 诊断说明 | 原规则下可请求，绝不声称预检全部通过 |
| 观察 stale，但无故障且允许重新核验 | 诊断说明 | 原路径更新证据，不新增全局锁 |
| 有真实工具故障或来源冲突 | 具体受阻原因 | 直达核对；弱检查不能清除既有故障 |
| 局部受阻，独立任务有效 | 受阻/可继续范围分列 | 按原授权、Auto 和预算请求独立工作 |
| 退出未确认、控制权处理中、必要授权缺失 | 明确暂停原因 | 保留硬门槛，不重放或换通道 |
| 旧端缺少摘要 | 旧协议兼容说明 | 沿用原动作与执行端核验，不因字段缺失锁死，也不伪造通过 |
| 离线或身份不匹配 | 连接/身份不可用 | 禁止提交，不回退其他节点 |

前端保留单次在途操作防重；切换视图不能解除该锁。旧响应按 owner/executor/session、round/seq、修订归属处理。若提交时条件变化，展示拒绝/等待及当前原因，不写重试、不自动打开 Auto。

### 4. 生效依赖与可选工作流分别展示

环境摘要扩展有界的生效依赖条目与依据：正式来源、有效显式声明、实际调用证据各自标识，不发送完整声明正文或环境变量。复用后端已有依赖解析与核验结果；渲染和状态广播不触发新发现。尚未核验的声明显示待核对，不能通过填充 UI 字段使其有效。

已绑定 OpenSpec 且无额外选择时，显示“OpenSpec · 来自任务来源”，将 `workflowRef` 的空值解释为“无额外工作流选择”，不解释为缺依赖。来源与显式声明并存时按依赖 ID 去重、保留两种依据；一个声明失效不能用另一个依据掩盖。用户只绑定 Skill 仍不产生必需依赖；清空 workflowRef 也不清空来源依赖和历史故障。

旧端无新依赖摘要时，只从明确已有来源/声明展示已知依据并标记核验范围未知，不从历史文本猜测。本变更不增加自动 workflow 选择、自动绑定或执行阶段授权。

### 5. 关联问题不丢失证据，也不把诊断变成配置任务

可靠的 source revision、check ID、decision evidence reference 可以连接同一事实。已有字段不足时仅添加有界关联引用，不把原始日志灌进摘要；无法证明同源的条目保持独立，不能仅凭文案去重。问题处理后重新消费当前摘要，仍有剩余问题时明确列出，不能在单张卡成功后显示全局就绪。

技术信息作为可折叠证据：Backend、access、transport、CLI 版本服务于核对，不作为用户必须理解的必填项。说明只围绕当前原因、受影响范围、需要谁做什么；访问拒绝本身不推断沙箱内部根因。已被拒的真实文件、权限和隔离前置仍按已归档阻塞修复约束处理。

### 6. 现有规格冲突采用有序纠偏，不改历史掩盖问题

本变更沿用 `loop-workbench-experience` 的六个同名要求，完整重述最终契约，避免建立另一个功能相同却相互矛盾的主能力。冲突如下：

| 旧变更要求 | 本变更最终要求 |
| --- | --- |
| 删除顶层面板/流程与阶段轨道 | 恢复共享状态的两种一级视图和三阶段指示 |
| 评分、风险仅放诊断 | 主层恢复指标及分数环，仍不代替验收 |
| 流程与配置共用通用详情分类 | 流程为主区，来源/诊断/问题为定向辅助操作 |
| 一个主按钮随问题切换 | 稳定运行/恢复控制与独立问题处理入口 |

本次仅写本 change。未来用户授权同步/归档时，先处理旧 `refactor-loop-workbench`，再同步本纠偏变更，逐条以本变更全文更新同名要求，不把旧“删除主视图”的声明追加回来。当前主规格不存在该能力，所以 delta 使用 ADDED；届时若旧变更已建立主规格，应在该同步授权范围内将这六个同名要求改为 MODIFIED、保留全文并重新验证，而非带重复 ADDED 直接归档。若主规格已包含本方案，核对一致性即可；未知第三方冲突需报告，不能静默覆盖。

本变更同时提供 `loop-milestone-progress` 同名展示条款的完整 delta，以保留当前主规格“面板和流程一致”的既有语义，并替代旧变更禁止两种主视图的附加表述。实施交付须明确列出该协调项；apply 不执行同步或归档。来源、环境和里程碑同名条款均以本次 delta 为最终文本，其余任务/验收要求不变。

### 7. 用恢复清单和负面场景共同验收

前端单元测试覆盖：空 blockers + unsupported、无故障 stale、部分通过 + 既有 actual_tool 故障、未确认退出/incomplete、明确暂停、局部独立任务、来源冲突、旧端/离线、多问题同源/不同源、高分缺证据。

后端用 fake Backend 和临时目录验证动作摘要与原核验一致、summary 无工具 I/O、依赖依据一致、旧端字段兼容和拒绝路径不弱化；不运行生产 LOOP 或外部应用。

浏览器在 1366×768、390×844 及宽度切换时保存截图并实际检查：阶段轨道、一级切换、指标、分数环、宽流程、直接控制、Addon/策略/目标、具体问题路径、来源更换/解绑取消、辅助面键盘关闭与焦点返回、长文本无整页横向溢出。沿用 `loop-stage-details.spec.ts`、`loop-control-handoff.spec.ts` 的迟到响应和控制门槛；更新旧工作台测试中“核心可视化必须被删除”的断言，而不是删除安全和性能断言。

请求计数必须证明：切视图/开详情零执行与检查，正常页零自动发现，显式动作至多一次对应 RPC，隐藏详情/重复推送零额外读取，历史详情同一可见修订合并。截图与人工审美意见分开记录，结构校验不能冒充视觉验收。

## Risks / Trade-offs

- [恢复指标导致信息重新拥挤] → 只恢复原核心观测层，来源/诊断管理默认不铺开；窄屏局部换行与滚动，不用再次删功能解决。
- [显示摘要成为第二套权限规则] → 复用服务端既有判断，严格区分可请求与获准执行；边界复验和旧协议用例覆盖竞态。
- [仅改文案掩盖真实未选/失效声明] → 展示依赖来源和核验状态，不以来源有效掩盖显式声明失效。
- [恢复旧组件带回假成功或丢失修复] → 仅以 `26f3201` 为视觉参照，保留新 hook、回执和审计；高分/历史/断点夹具验证。
- [两个未归档 change 同名规格覆盖] → 明确有序同步与 ADDED/MODIFIED 重核，不在本轮暗改旧记录，未来同步前对照冲突表。

## Migration Plan

1. 按本设计固定合成夹具与恢复清单，记录当前基线，先完成摘要/投影语义，再接入视图和操作面。
2. 复用已有 Session、LoopRecord 和策略字段；新增反馈字段向后兼容，不重写旧记录、不迁移真实用户数据。
3. 完成单元、fake Backend、浏览器交互及截图检查后更新 `docs/loop-adaptive-delivery.md` 与对应 AGENTS 入口说明，明确真实平台/人工视觉未验边界。
4. 本变更不自动部署。若后来需要 UI 回退，仅回退本次展示和兼容摘要；不倒退控制权、隔离及阻塞保护，不清空状态或启用 Auto。
5. 后续同步/归档需新的明确请求，并执行决策 6 的冲突核对；不把完成本任务清单视为发布或归档授权。
