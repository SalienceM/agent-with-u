# Spec Delta

## MODIFIED Requirements

### Requirement: 依赖声明不等于任务来源或授权

系统 SHALL 仅对当前明确工作流、有效声明或实际调用证据所关联的依赖做定向检查，保留依赖来源及适用范围。安装或绑定 Skill、历史文本出现工具名称或模型建议 MUST NOT 单独形成必需依赖、正式 change 绑定或新的执行授权；不明确的工作流选择 SHALL 允许用户显式指定且不启动任务。界面 SHALL 展示实际生效依赖及其正式任务来源或显式工作流来源，而非只依据可选工作流选择是否为空；来源绑定与工作流选择 SHALL 保持独立语义。

#### Scenario: 未绑定来源的明确工作流
- **WHEN** LOOP 没有正式任务来源绑定，但当前有可重新核对的显式 OpenSpec 工作流选择和有效 CLI 声明
- **THEN** 系统检查该工作流的 CLI 依赖，仍保持任务来源未绑定，不猜测最新 change、不扩大原工作流阶段

#### Scenario: 通用 LOOP 绑定了多个 Skill
- **WHEN** 普通探索 LOOP 只是安装或绑定了 OpenSpec Skill，没有选择该工作流且没有实际依赖证据
- **THEN** 系统不因 OpenSpec 缺失而阻塞该 LOOP，也不探测所有已绑定 Skill 的 CLI

#### Scenario: 声明被修改或选择不明确
- **WHEN** 已选择工作流的命令声明失效、发生冲突，或旧交接无法可靠定位当前工作流
- **THEN** 系统标明声明失效或工作流未确认，只对明确受影响工作等待选择，不执行旧声明、不解析历史授权，用户选择依赖不会自动绑定来源或运行工作流

#### Scenario: 已绑定来源而没有额外工作流选择
- **WHEN** LOOP 已显式绑定 OpenSpec change，其任务来源需要 OpenSpec 依赖，而没有单独选择工作流
- **THEN** 界面显示“OpenSpec，来自已绑定任务来源”及核对状态，不显示为缺少必填工作流，不要求再选一次才能操作；绑定仍不代表批准工作流的其他阶段

#### Scenario: 多种依赖依据并存或声明失效
- **WHEN** 同一依赖同时来自正式来源与显式工作流，或其中一个依据失效
- **THEN** 显示去重的依赖和各自依据/有效性，不混淆 change 与命令；有效来源不能掩盖另一个声明失效，解除条件保持原适用范围

#### Scenario: 选择通用模式不解除既有依赖
- **WHEN** 用户清除可选工作流选择，但仍有正式来源或已知故障
- **THEN** 来源要求的依赖和未解决故障继续显示并受原规则约束，不把通用模式作为绕过门槛的开关

### Requirement: 环境状态轻量展示并安全持久化

系统 SHALL 在 LOOP 面板、流程详情及恢复后展示一致的访问策略、检查覆盖、原因和解除条件，提供空闲时的显式重新检查入口。正常、未知或仅覆盖不足且没有已知阻塞的环境 SHALL 通过按需诊断查看，不占据常驻大卡；当前已知阻塞和退出未确认 SHALL 通过具体问题入口可见。记录 SHALL 按用户、节点、Session 及修订隔离，使用有界摘要和按需详情，不保存完整环境变量、凭据、授权令牌或额外历史正文；旧记录 SHALL 保持未知。

#### Scenario: 重新检查不等于执行
- **WHEN** 用户在空闲且有操作权限的 LOOP 点击重新检查环境
- **THEN** 系统仅运行所选环境的固定只读检查并更新证据，不开启 Auto、不发送任务模型调用、不自动恢复暂停；运行中或人工接管只读视图不提供此操作

#### Scenario: 延迟响应与配置修订
- **WHEN** 用户切换 Session、节点或环境配置后旧检查返回
- **THEN** 旧结果只属于原身份和修订，不覆盖当前就绪状态、不解除新暂停，重复推送和隐藏视图不形成详情轮询

#### Scenario: 旧记录及敏感信息
- **WHEN** 加载无环境字段的旧记录，或异常包含密钥、完整环境和私有正文
- **THEN** 系统在诊断中显示旧环境未知；新记录仅保留白名单化类别及必要身份引用，敏感正文不进入环境详情、紧凑推送或日志

#### Scenario: 环境问题的日常表达
- **WHEN** 当前存在阻止执行的确定环境故障
- **THEN** 主界面用简短原因和影响范围说明暂停，处理入口直接展开相应检查和解除条件；Backend、角色、原生访问策略、CLI 版本和完整依据在技术详情中可查，不要求用户先理解这些术语才找到动作

## ADDED Requirements

### Requirement: 检查覆盖与故障门槛分别表达

系统 SHALL 将预检是否受支持、检查覆盖范围、已有故障及当前操作资格分别表达。“不支持”“部分覆盖”或无阻塞的过期观察 MUST NOT 单独制造新的运行禁用条件，也 MUST NOT 显示为全部检查通过。已有真实故障、证据不完整导致的门槛、权限/安全暂停和退出未确认 SHALL 继续按现有规则保护；新的弱检查不得覆盖或清除这些事实。

#### Scenario: 不支持检查但没有故障
- **WHEN** 预检不支持，已有进程已确认退出，且没有适用故障或其他门槛
- **THEN** 诊断显示无法预检及覆盖限制，用户可按原规则显式请求执行；不引导不断点击重新检查或改权限，不给出就绪或验收保证

#### Scenario: 部分覆盖与既有实际工具故障并存
- **WHEN** 最近原生策略内检查通过或不支持，但保留实际工具路径的故障
- **THEN** 问题区继续显示实际故障、影响与解除条件，不以最新较弱检查替换已有故障，也不借恢复按钮绕过它

#### Scenario: 退出未确认或记录不完整
- **WHEN** 检查退出未确认或环境记录不完整且按原规则不能解除阻塞
- **THEN** 界面保留相应禁用条件及核对路径，不把这种状态当成普通非阻塞的覆盖不足

#### Scenario: 未发生环境故障的观察失效
- **WHEN** 旧检查结果过期，但没有真实阻塞，当前执行身份仍可经原流程核验
- **THEN** 界面显示证据需更新，不将旧观察自动变成全局环境故障；执行请求仍服从当前身份的核验与其他既有前置
