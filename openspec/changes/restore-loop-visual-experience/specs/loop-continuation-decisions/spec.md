# Spec Delta

## ADDED Requirements

### Requirement: 运行操作资格与问题排序分离

系统 SHALL 将问题展示的严重程度与“可请求运行/恢复”的资格分别表达，依据当前执行端身份、状态和已有门槛生成操作反馈。允许请求 MUST NOT 等同于保证执行成功、预检全部通过或扩大授权，执行端 SHALL 在请求和实际调用边界重新核验。非阻塞诊断、问题数量或前端排序 MUST NOT 单独禁用运行；实际硬暂停、范围无法核对、已有环境故障和退出未确认 MUST NOT 因界面恢复而被清除。

#### Scenario: 仅预检不支持且无已知阻塞
- **WHEN** 当前预检为不支持或覆盖不足，没有已知故障、未确认退出或其他阻止该动作的条件
- **THEN** 用户仍可按原规则请求运行/恢复，界面不要求先把预检变成通过；执行保持原受限路径，未知覆盖不显示为已验证

#### Scenario: 局部任务受阻但存在独立任务
- **WHEN** 执行端已确认受影响任务和独立就绪任务，且原授权、Auto、预算与高优先级条件允许
- **THEN** 界面保留局部问题且如实显示可继续范围，不因警告优先级禁用独立工作，不替执行端自己挑选任务或放行受阻测试

#### Scenario: 用户恢复尚未完成的判断
- **WHEN** 处于需要用户显式恢复的旧暂停或无进展暂停
- **THEN** 查看提示、重新检查或刷新不解除暂停；只有明确恢复请求才进入既有重新核验流程，仍不豁免必要授权与验收

#### Scenario: 动作提交期间状态变化
- **WHEN** 用户看到可请求状态后，控制权、来源修订、Backend、预算或旧调用状态发生变化
- **THEN** 执行端按新状态拒绝或等待，界面展示真实结果，不重试写请求、不沿用过期可用状态启动任务

#### Scenario: 旧执行端或离线
- **WHEN** 执行端未提供新式动作摘要或当前连接不可用
- **THEN** 旧执行端使用已知旧协议的原动作与权威核验且保留明确硬门槛，未知不显示为通过；离线时禁止提交并显示连接原因，不回退其他节点，不从提示优先级创造新的权限结论

### Requirement: 问题处理动作具有明确对象与副作用

系统 SHALL 为阻塞问题提供对应原因、影响任务或执行范围、证据来源、解除条件和明确动作对象。环境复查、来源核对、范围确认、工作流选择与运行恢复 SHALL 保持独立操作和反馈；问题导航本身 MUST NOT 执行这些动作或启用 Auto。相同身份与因果引用的问题可合并展示，但未解决问题和历史损失 MUST 保留。

#### Scenario: 复查完成后仍未恢复
- **WHEN** 用户完成来源核对或环境复查
- **THEN** 界面分别显示本次核对结果和当前运行资格，仍有问题时列出剩余条件；不会自动续跑、清空其他阻塞或把检查通过显示为任务验收完成

#### Scenario: 定位后问题已变化
- **WHEN** 用户打开某项处理面后问题被更新或修订失效
- **THEN** 表单标明当前结果或要求刷新，旧操作不得应用到新身份/修订；不存在处理对象时返回问题已变化而不跳到另一个问题执行
