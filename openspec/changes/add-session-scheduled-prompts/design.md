# Design

## Context

动机与范围见 [proposal.md](proposal.md)。用户已确认向指定已有 Session 定时发送预设指令，并授权捕获这组规划工件；下述产品默认作为本提案的设计选择，不表示已创建定时任务或用户已逐项设置偏好。

现有 `SequenceScheduler` 在 `ws_main.py` 启动，负责普通 Session 串行派发、运行注册、暂停及重启恢复，已不依赖前端在线。`ChatExtras` 独立保存队列，避免与聊天流式保存竞争；但队列没有日历规则或持久触发身份。`_rpc_seqtaskSetAuto(true)` 会把错误项重置为待执行，不能作为定时唤醒入口。实际聊天入口继续检查项目写预留、控制权、更新状态及原生进程退出。

`session_collaboration_store.py` 已采用 owner/executor 范围、SQLite 短事务、CAS 和 requestId 回执。新存储沿用这些协议模式，避免把逐次触发和时间索引塞进 Session 聊天 JSON。远端路由由当前 Session 的所属节点决定；客户端连接状态不能证明执行端进程已停止。桌面“完全退出”会停止本机 Backend，与关闭页签不同。

本变更跨持久化、调度、消息关联和 UI，且存在跨存储提交与断线恢复边界，因此需要独立设计文档。

## Goals / Non-Goals

**Goals:**

- 让同一触发在断线、重复请求和执行端恢复后保持唯一关联，可定位到原队列项及聊天轮次。
- 区分时间已到、已入队、真实运行、等待用户、结束和结果未知；派发成功不代表指令目标达成。
- 把时间触发接入现有执行链路，保留串行、暂停、身份及运行守卫。
- 用有界状态和按需详情支持弱网，提供真实可展开输出。

**Non-Goals:**

- 不实现分布式迁移、系统唤醒、云端代跑、任意 cron 表达式、附件模板或每次创建独立 Session。
- 不承诺外部工具副作用的 exactly-once；无法确认是否开始时宁可显示未知，也不重新运行。
- 不把模型推理、读取页面或定时配置保存当作授权来源；不复制单次 Kit 委托、workspace lease、动态令牌或隐藏思考。

## Decisions

### 1. 执行节点拥有计划，复用普通聊天入口

新增执行端 `SessionPromptScheduler`，与 `SequenceScheduler` 一同启动和关闭；先恢复队列及未确认执行，再开放定时派发。它只计算到期项、持久化触发意图并去重入队，不直接启动另一套 Backend，也不调用 `seqtaskSetAuto`。真正运行仍走现有主轮次入口。

UI 关闭、Relay 断线只影响观测。执行端更新阻塞期间暂停新派发；进程停止或系统休眠期间没有执行能力，恢复后按错过策略处理。目标 Session 的实际 owner、普通类型、Backend 可用性、工作目录和执行守卫在开始前再次检查；类型变化、目标删除或归属变化时保留原因并阻止运行，不能按名字重建或转投节点。

替代方案：前端计时会随窗口和网络丢失；操作系统 cron 难以接入跨平台身份、队列和 UI 状态。两者均不采用。

### 2. 持久计划、触发实例与请求回执分开

在 `paths` 管理的数据目录新增专用 SQLite sidecar，由 `session_schedule_store.py` 管理。共享既有身份、规范 JSON 和回执设计，但使用独立表与到期索引，以便一个事务内同时推进时间游标、建立触发和记录回执。数据库访问使用串行的有界后台工作队列，不能让 SQLite 锁等待阻塞 WebSocket 事件循环。

| 记录 | 主要字段与不变量 |
| --- | --- |
| Schedule | `id / owner / executor / sessionId / revision / enabled / title / prompt / rule / timezone / misfirePolicy / nextDueAt / consumedThrough`；目标 ID 创建后不可改名替换，配置变更 CAS |
| Occurrence | `id / scheduleId / scheduleRevision / scheduledAt / coveredThrough / coalescedCount / promptSnapshot / state / taskId / userMessageId / assistantMessageId / timestamps / error`；创建时冻结文本，时间范围只能合并尚未开始的项 |
| Request receipt | owner/executor 范围内的 `requestId / intentDigest / status / result`；同一请求相同意图返回原回执，不同意图拒绝 |

触发的唯一键由所属身份、计划 ID、计划修订和原定 UTC 时点组成；队列 ID 与消息 ID 从已持久触发身份派生，禁止每次恢复重新产生时间戳 ID。显式重试创建独立 attempt ID 并引用原失败项，保留原记录；自动恢复从不创建重试 attempt。

计划开关、时间规则是否耗尽、运行状态和连接状态分别保存/显示。单次计划生成实例后仅耗尽其下一时点，不能因没有下一时点而取消该实例的派发资格；用户禁用仍取消未领取实例。等待 Session 空闲、队列暂停或审批是运行原因，不伪装成模型正在生成。近期详情分页，终态正文可按容量归档；消费游标、未决记录及去重所需最小回执不得随历史清理丢失。

替代方案：直接给 Session JSON 添加定时数组会与逐消息保存竞争；仅靠内存计时或客户端 UUID 无法恢复原触发。复用通用 records 表也不利于到期索引和计划/触发原子提交，因此采用专用 sidecar。

### 3. 有界时间规则与时区语义

首版实现单次、每天、每周多选和固定间隔（最短一分钟）。计划保存显式 IANA 时区，不依赖查看者系统时区；预览来自目标执行端同一计算器，显示本地日期、UTC offset、时区和下一次时点。固定间隔以首次设定的 UTC 锚点计算，不从上次完成时间重新计时。

每天/每周按当地墙钟时间计算：夏令时缺失的时刻跳过，重复时刻仅取较早的 UTC 实例一次。单次若当地时间不存在则拒绝，若歧义则要求从明确 offset 中选定。Windows/冻结分发需携带可用的 `tzdata`；缺失或未知时区明确不可保存，不退回本机时区。时间库依赖仅在实际实现/打包时纳入，不在捕获规划时安装。

等待采用单调时钟，但每次唤醒重新校验 UTC 到期时间；最多每 30 秒以及配置变化时重算。时间倒退不能越过持久消费游标重放，时间前跳按错过规则合并，长时间离线不得逐分钟枚举历史。普通调度抖动留 60 秒宽限；超过宽限且尚未生成的时点才应用错过策略。

提案默认 `catch_up_once`：将恢复时已错过的时点合并为一个实例，保留首次/末次时间与次数。可选 `skip`：记录已跳过范围并推进到未来，不调用模型。单次错过后分别补跑一次或终结为已跳过；配置禁用期间不补历史，重新启用从未来时点开始，已过期单次需先改为未来时间。既有已入队实例继续保留，不因 `skip` 被重新解释成未入队的错过项。

替代方案：只保存本地时间字符串无法跨节点解释；每次完成再延时会漂移；全部补跑会在恢复后突发。上述选择给出固定、可预览、可验证的结果。

### 4. 忙时串行、合并积压，保留用户暂停

到期项追加在当前普通队列末尾，不抢占、不引导当前轮。一个计划最多一个未开始实例；若已有待执行项，继续扩大其覆盖时间和次数，不再追加；若当前实例正在运行，最多额外保留一个后续待执行实例。多个计划保持各自身份，按原定时点、计划 ID 稳定入队，不插到已有手动消息之前。

暂停和错误仍由既有队列管理。定时到期只能留下待执行项，不能打开 Auto、清除错误或解除原生未知退出。手动停止当前轮继续暂停整个 Session 队列。定时失败保留原输出并停止后续派发；显式“重试并继续”若包含定时失败项，必须显示目标并建立新 attempt，不能把原 occurrence 重写为未执行；未知退出须先按既有机制核对，普通恢复也不能跳过。

定时队列项的文本由计划修订冻结。首版队列内不直接改其文本，入口引导编辑计划；允许显式取消某次待执行项，并写入取消结果，不能删除后被调度器重新生成。普通队列项的编辑、调序和重试保持原语义。

替代方案：中断当前轮会改变用户正在进行的任务；无限积压会让周期任务失去时效。仅限制每计划的待执行实例既保留提醒，又避免恢复风暴。

### 5. SQLite 与队列的交接可恢复，不假装一个事务

队列 sidecar 与 SQLite 没有共同事务，采用持久 outbox 与稳定 ID 对账，给定时项增加派发前闸门。所有涉及同 Session 的定时变更、入队、领取和取消必须经过同一调度协调器；磁盘工作可异步，但不能出现未受保护的并行保存或旧快照覆盖。

1. 在 SQLite 短事务中消费到期时点并创建 `prepared` 实例，冻结配置与消息 ID。
2. 向目标队列幂等追加同一个 task ID，原子落盘后才能将 occurrence 标为 `queued`。此时若崩溃，只读比对两边即可完成对账。
3. 派发前核对该计划仍启用、修订匹配、取消未提交以及现有运行守卫；CAS 领取 occurrence 为 `claimed`。拿到派发资格后再次核对 Session 控制边界，持久队列 running，再注册真实轮次。领取之后的进程退出均保守处理。
4. 在真实轮次开始后记录 `running`；终态由权威任务退出及聊天保存回执归约。早到 `done` 文本帧、HTTP/RPC 成功或队列接收都不是完成证据。

| 恢复断点 | 处理 |
| --- | --- |
| 已写 prepared，尚未写队列 | 确认计划仍有效且无领取记录后，补齐同 ID 队列项 |
| 队列已写，queued 回写丢失 | 根据同 ID 和配置指纹对账，不能新增条目 |
| 编辑/关闭已提交，但旧队列项仍在 | 派发闸门拒绝旧修订并完成取消对账 |
| claimed/running 后退出，缺少终态 | 标为结果未知并保留阻塞；不因队列项缺失判定未执行 |
| 已有可核验终态、摘要尚未更新 | 从原轮次/消息关联补齐状态，不再调用模型 |
| 两侧缺失、冲突或损坏，无法证明未开始 | 标记恢复受阻，保留可用证据并停止该目标派发 |

以上提供触发关联去重及保守恢复，不能证明模型调用的外部写操作仅发生一次。

### 6. 编辑、启停和删除有明确生效边界

计划写操作先在线检查目标权限，再按 `expectedRevision + requestId` 提交。禁用、删除和改变文本/时间规则均递增修订，并在同一事务中取消旧修订未领取实例，写出待清理队列意图。成功回执意味着旧待执行项已不可获得派发资格，即使展示清理尚未完成。

若运行已先获得 `claimed` 资格，返回其真实关联并区分“本次正在启动”和“本次已运行”，明确修改影响后续；不能把领取资格当作模型已经输出。停止本次继续使用聊天停止入口，启动窗口内也必须可接收停止意图并在进入真实轮次前重查。删除计划保留已运行的历史和必要去重墓碑。删除 Session、转为非普通 Session 或 owner 失效均在实际开始前阻止派发；关闭/隐藏客户端页签不是删除，也不关闭任务。

配置写超时显示结果未知，保留草稿和 requestId；恢复连接时合并一次只读回执核对，后续可手动刷新，不自动重发写入。只有服务端原请求回执及修订匹配才能清除原草稿，新编辑不被迟到回复覆盖。

替代方案：先删队列再关计划存在再次入队窗口；收到网络异常直接撤回本地 UI 会误报未生效。先提交权威修订，再做可重入清理可封住派发窗口。

### 7. Session 范围协议与权限保持一致

通过 BridgeWS 暴露建议命名的 `sessionScheduleList/Get/Preview/Save/SetEnabled/Delete/RequestStatus/Occurrences`，每个接口显式携带 Session ID 并走该 Session 节点路由。写操作携带稳定 requestId 和基线修订；读取只返回所属 owner/executor 的记录，列表不带完整指令和聊天正文。通过能力版本发现支持情况，旧节点不可用时直接说明，不用旧队列接口模拟。

开始执行时读取 Session 当前 Backend、model override、reasoning effort、工作目录和普通权限，记录本次实际使用的非敏感运行元数据；不可用时失败并显示原因，不自动换模型或执行节点。指令中的应用命令遵循现有执行端队列语义，不把不支持的命令静默改成模型文本。

创建/启用计划只授权按该配置提交普通聊天，不复制此前的单次工具委托。需要新的人工审批或输入时呈现真实等待状态；没有控制端就按原生能力等待或明确失败，不能自动回答、猜测授权或借用历史 workspace lease。

### 8. 可见输出与弱网负载

Session 入口显示启用数量和最近状态；设置表单包含预设文本、规则、时区、错过策略、下一次预览，以及“保存并启用/保存为停用”。历史区按需展开，列出原定时间、实际开始时间、状态和直达原消息入口。用户不打开详情也能看到排队、暂停、运行、等待回答、失败或未知原因。

消息使用独立、经过白名单归一化的 `scheduleRef`（计划 ID、修订、occurrence/attempt ID、原定时间），不把定时来源伪装成已有 Skill `workflowRef`。活动输出直接复用该 Session 的真实 `streamDelta` 和持久聊天消息，不再生成另一份摘要或隐藏输出窗口。

定时摘要通过 `sessionScheduleUpdated` 携带 identity、revision 和小型状态变化；不含完整历史，不逐 token 发送。面板关闭不加载详情；重连时按 Session 合并状态查询，用原消息 ID 恢复可见输出。断线保留已收到文字并标明最后同步时间，不能把离线缓存标为仍在实时更新。旧身份、旧修订和另一节点的迟到响应一律忽略。

替代方案：每个计划轮询、每条流式文本重载历史会放大弱网延迟；复制独立输出容易产生两个终态。复用现有消息流及紧凑状态可保持单一可见结果。

## Risks / Trade-offs

- [跨存储崩溃窗口] → 先有持久触发，再写队列；派发前核对领取记录；故障注入覆盖每个提交边界。不能证明未开始时保留未知。
- [执行端发布、磁盘/数据库繁忙拖慢同步] → 有界后台存储队列、短事务和批量到期处理，主事件循环只接收完成通知；检查高频触发不会阻塞停止和状态读取，不承诺机器过载时准点。
- [模型长期不结束或等待人工输入] → 同 Session 串行与每计划积压上限，显示真实等待；不以超时自动杀进程或重试。
- [默认补跑可能执行过时指令] → 保存时展示明确错过策略，允许选择跳过；多次错过只补一次，实际运行遵守当前暂停及权限。
- [同一数据目录启动两个调度进程] → 对定时执行取得本机独占锁；第二个进程只能报告不可调度，不能同时派发。锁恢复不解除 occurrence 的未知状态。
- [时区规则变化和时钟校正] → 保存明确时区/规则并复用同一预览器；去重以已消费时点为准，DST 与时钟跳变测试必须覆盖。
- [旧客户端仍可编辑队列] → 定时元数据在通用队列修改边界验证，保留已取消/已领取账本；缺失或不匹配的条目不能自行重新生成。

## Migration Plan

1. 新存储按 schema version 初始化，旧 Session 默认无计划；旧队列项没有定时字段时按原流程处理。不迁移或启用既有聊天文本。
2. 先实现存储、计算器、恢复与派发闸门，再发布协议和 UI 能力；恢复未完成前不开放新派发。
3. 在隔离数据、fake Backend 和弱网 fixture 完成规格验证后才进入正常发布流程。本变更规划不提交 Kit、真实任务或安装。
4. 回滚前显式关闭定时派发并检查真实在运行轮次。旧版本不理解定时队列标记，因此不能直接带着未开始的定时项降级；需清理这些已禁用项且保留账本，已运行或未知项继续保留保护。无法确认时先停止降级，不靠删除记录解除风险。
