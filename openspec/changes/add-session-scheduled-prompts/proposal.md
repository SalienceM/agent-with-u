# Proposal

## Why

用户希望在指定时间向已有 Session 提交预设指令，沿用该 Session 的上下文，无需届时打开窗口手动发送。远端连接不稳定、Session 忙碌或执行端重启时，需要明确区分尚未执行、正在执行和结果未知，并避免重复触发及不可见等待。

## What Changes

- 在普通 Session 增加“定时”入口，创建、查看、编辑、启停和删除定时指令；配置时间、时区、预设文本及错过时间的处理方式，保存前预览下一次运行时间。
- 本提案以单次、每天、每周和固定间隔为首版时间规则，执行时使用目标 Session 当前的 Backend、模型、上下文和普通权限设置。
- 定时任务由 Session 所属执行节点持久化和调度；关闭 Session 页签或远端窗口断线不停止已保存任务。执行端完全退出或休眠期间不能执行。
- 到点后进入现有串行队列，忙时等待，不打断当前轮次；每项计划最多保留一个未开始的触发实例，后续到期合并。暂停、失败及未知退出仍阻止自动派发。
- 提议默认在执行端恢复后合并补跑一次，并允许选择跳过错过的时点；已开始但结果未知的执行不适用补跑，必须保留核对状态。
- 使用持久触发编号、请求回执和修订检查处理重复提交、弱网断线、乱序事件及重启；网络超时不能被当作未提交，禁止隐式重发。
- 原聊天显示定时来源、真实运行状态和流式输出；历史详情按需读取，断线保留已收到的内容，重连只核对原执行。
- 首版限定普通 Session 和文本指令；不创建新 Session，不改变 LOOP/AIMEIN 推进语义，不增加无人确认发布/安装能力，也不保存单轮 Kit 委托或临时工具令牌。

已确认的产品目标为“到点在指定 Session 执行预设指令”，本轮确认仅授权形成规划工件。上述时间规则和补跑方式属于提案中的设计默认，不记录为用户已经逐项选择的偏好；实际任务仍需用户填写并保存启用。

## Capabilities

### New Capabilities

- `session-scheduled-prompts`：已有普通 Session 的定时指令配置、执行端持久调度、去重入队、恢复规则及运行可见性。

### Modified Capabilities

无。复用普通聊天、序列队列和身份边界，不修改已有 LOOP 继续执行、控制权交接和原生执行环境的规格。

## Impact

- 后端：新增定时计划与触发记录的持久存储、时间计算和调度模块，经 `BridgeWS` 提供 Session 范围的配置与只读状态接口；接入 `ws_main.py` 生命周期。
- 执行链路：扩展 `SequenceScheduler`、`chat_extras_store.py` 的定时来源与稳定消息关联，继续通过实际聊天轮次注册和既有执行守卫派发；不能把 `seqtaskSetAuto(true)` 用作定时唤醒。
- 前端：Session 入口、定时设置与运行历史、`SeqTaskPanel`/消息来源标记、`api.ts` 节点路由与断线恢复；不新增逐任务轮询或逐 token 全量状态同步。
- 存储与依赖：复用本机 SQLite、请求幂等和修订模式，定时数据与聊天正文分离；时区采用 IANA 数据，需核对 Windows/冻结分发中的数据可用性。不引入云端 cron 服务或系统开机唤醒。
- 验证：可控时钟、隔离临时数据、fake Backend、重启断点及弱网浏览器 fixture；不运行生产定时任务、真实模型、发布或安装。
