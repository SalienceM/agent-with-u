# Proposal

## Why

用户只想把普通分支副本合回原来的主 Session，现在却要辨认额外的整合 Session、查找历史记录、手动核对候选并切换多个页面；冲突解决后仍显示旧冲突，笼统的“未提交”也无法说明是哪一侧的问题。需要把现有可靠的 Git 合并能力组织成一条可理解的操作流程。

## What Changes

- 副本右键“合并到主 Session”进入单一面板，固定真实父子关系，优先恢复这对来源/目标的既有未完成操作；只有用户明确新建时才生成另一条记录。
- 面板持续显示“副本 → 主 Session／目标分支”，按当前状态突出一个下一步：查看变化、确认准备、处理冲突、确认应用或查看结果。准备和最终应用仍分别审阅并确认冻结计划。
- 独立整合 worktree 与 Session 保留在后台，默认不作为第三个普通副本占据左侧树；冲突时展示处理入口，也能按需打开工作区、日志和历史。既有整合会话、标签和深链接仍可访问。
- 准备完成、修复实际退出或返回面板时，合并有限的自动 Git 核对；冲突消失后刷新状态。自动核对不启动修复、不运行测试、不应用合并。
- 阻塞提示明确对应来源、主 Session 或整合空间，列出脏文件、未保存缓冲区、活动或未知结果，并提供定位入口。Git 核对与项目测试结果分别展示，缺少测试证据时保留“未验证”。
- 最终成功回执显示实际更新的原目标分支和提交，保留副本及整合成果；不自动 push、清理或切换目标分支。
- 支持持续多分支开发：合入主干后在首屏提供“同步主干到此分支”，也可在下一轮开发前预览同步；复用原分支、Session 和独立确认，正常同步快进，分叉时保留双方历史。
- 在分支副本面板直接嵌入横向 Git 分支图及下方提交记录，显示真实父提交、主干/副本 HEAD、领先/落后和未提交状态，点提交查看文件差异。目标是减少并尽早暴露冲突，不承诺任意并行修改都没有冲突。

## Capabilities

### New Capabilities

- `branch-merge-workflow`：基于既有隔离合并服务的连续操作面板、整合空间呈现、既有记录恢复、阻塞定位和验证结果分层。

### Modified Capabilities

无已归档主规格需要修改。`parallel-session-workspaces` 尚位于已完成但未归档的 `add-session-collaboration-and-input-workflows` change；本提案沿用其 Git 隔离和两层父子关系，仅收敛合并交互。其“整合 Session 与副本同为主项的第二层”在数据关系上保留，普通列表可见性由本 change 明确调整；实施时须同步该待归档场景，不能留下相互矛盾的展示承诺。

## Impact

- 前端：`ProjectMergePanel`、`ProjectTasksPanel`、`Sidebar`、`taskSessionTree`、相关类型/API 与协作读取控制器；复用 `WorkflowControls`、主题和可访问性约定。
- 后端：`project_merges.py`、协作摘要/记录读取及 `workspace_tools.py` 的受控查询能力；提供可定位的状态投影，保留 owner/executor/origin 校验、冻结指纹、独立确认与 `project_write_gate.py` 写入保护。
- 验证：隔离仓库的合并回归、桌面/窄屏浏览器流程、断线/迟到结果与旧记录兼容；更新 `docs/session-collaboration-workflows.md` 和对应项目约定。
- 无新增外部依赖；不改 Git 合并算法、不开展跨节点合并、不放宽现有权限、不在本提案阶段改产品代码或执行发布。
