# Design

## Context

动机见 `proposal.md`。本设计基于已存在的合并服务，而不是重新设计 Git 工作区：

- `ProjectMergePanel.tsx` 把新建、历史、Prepare/Start/Verify/Apply/Cancel 分散成多个同等级按钮；重开默认落在新建页。`useCollaborationRead` 已支持身份隔离、按修订读取和事件合并，可继续复用。
- `project_merges.py` 冻结来源和目标，创建独立 worktree 与普通整合 Session，核对干净工作树、共同仓库和双亲历史后才允许目标 `--ff-only`。`git_verified` 没有运行项目测试。
- `taskSessionTree.ts` 同时把 `task` 和 `integration` 归入普通两层树，因此用户看到额外的第三个会话。Session 的父关系可以保留，呈现不必相同。
- 旧记录含 `sourceSessionId`（操作发起归属）、`source.sessionId`（Git 来源）、`target.sessionId`、`integration.sessionId`；发起归属与 Git 来源未必相同，不能混用。现有聊天接口按发起 Session 校验操作，不提供原操作发现列表。
- `project_write_gate.py` 保护目标活动、未保存缓冲区和未知退出。主 Session 中正在进行的聊天也可能阻塞最后应用；只切换页面不会让运行结束。
- 2026-11-08 对真实整合候选 `a01c385b3427d944def30e95215ff549094c5cfe` 做了操作核对：原记录仍显示冲突，手动 Verify 后才更新为候选。19 项 `TaskWorkspaceTests` / `ProjectMergeTests` 在独立较短 TEMP/DATA_ROOT 中通过（164.708 秒，退出码 0）；旧深路径下的失败仍是需记录的测试环境限制。这些是本次既有候选的定向证据，不是拟议新界面的验收，也不证明所有用户机器或全部测试通过。

## Goals / Non-Goals

**Goals:**

- 用服务端原操作驱动一个连续面板，减少导航、重复预览和人工核对；明确哪些自动动作只是查询或检查。
- 保留冻结计划、独立确认、原归属、目标排他保护和未知结果恢复，把它们投影为可操作的状态。
- 让普通副本继续使用完整 Session 能力；整合 Session 只作为这次合并的处理空间。
- 形成副本开发 → 合入主干 → 同步主干回原副本 → 继续开发的循环；可见的真实分支图帮助及时发现落后，不把 Git 历史图当作无冲突证明。

**Non-Goals:**

- 不做 rebase/squash 策略选择、PR 服务、跨节点合并、自动提交用户文件或自动清理。
- 不增加隐式模型调用、通用测试执行器或由模型文字决定的验收门槛；未配置的项目测试不成为新的永久阻塞。
- 不解除活跃主 Session 的保护，不让聊天令牌冒用另一 Session，也不把准备确认扩大为最终应用授权。

## Decisions

### 1. 服务端原记录是唯一状态来源，前端只选择呈现与下一步

为面板抽出身份键为 owner/executor/origin/operation 的控制器，保留原 operationId、修订、未知回执和进行中请求。业务阶段采用现有状态，增加显示投影而不保存另一套可冲突的状态机：

| 实际条件 | 主展示 | 主动作 |
| --- | --- | --- |
| 尚无预览 | 副本 → 主 Session／分支，变化范围 | 查看变化 |
| preview | 冻结来源、目标、目录、配置与影响范围 | 确认准备 |
| preparing | 正在准备独立候选 | 等待回执 |
| conflict | 冲突文件与处理空间状态 | 打开处理空间；启动修复另需明确操作 |
| candidate、尚未核对 | 正在核对／核对失败 | 自动有界核对；失败时手动重查 |
| candidate、当前核对有效 | Git 与测试分别展示、原目标与候选提交 | 确认合并到主 Session |
| blocked / error | 具体原因、对应 Session 与恢复入口 | 处理原因或显式重新预览 |
| applying / unknown | 应用中／结果未知 | 等待或查询原操作 |
| succeeded | 已更新原目标分支及最终提交 | 合入主干后同步回副本；同步成功后返回原副本继续开发 |

历史、取消、完整目录与日志置于次级区域；取消仍保留成果。复用 `WorkflowControls`，主表面使用不透背景，390px 窄屏用纵向布局，键盘关闭/返回有明确焦点。与引入独立全屏合并工作台相比，这个选择保留既有入口和草稿，避免再多一个工作场所。

### 2. 恢复原操作，而不靠新建预览“刷新”

扩展受控的、只读的合并记录发现能力（建议 `merge_operations` / 对应前端查询），返回有界分页摘要：operationId、originSessionId、实际来源/目标 ID、时间、状态、修订、短 OID 和可打开的原入口。查询必须限定 owner/executor 和当前有权访问且相关的 Session，不按标题推导，不扫取全量正文。

副本入口优先匹配真实来源/父目标：唯一未完成记录自动读取；多条明确选择；历史完成记录保留查看。父 Session 的入口只读展示关联状态并打开原操作上下文。写请求仍由原 origin 进入相同服务并逐项检查访问权；聊天中的 `session` 参数不变成任意 origin 代理。拒绝简单取消 `_merge_row` 归属检查，也不把新的预览当作旧操作重试。

旧节点没有此能力时，使用已有副本历史入口并提示兼容限制，不自动创建新操作兜底。重连恢复原 ID，requestId 绑定已提交意图并复用查询；只有明确的新用户动作才产生新的写请求。

### 3. 整合 Session 保留数据关系，普通副本树按用途投影

对存在可验证 merge 关联的 `relationKind=integration`，普通 Sidebar 副本区默认不生成普通子项，也不计入副本数量。源副本/合并入口显示紧凑“合并处理中／需处理”提示；面板内保留“打开处理空间”“返回合并”。按需查询精确关联，摘要携带必要关联 ID，避免按名称寻找。

已有活动标签不关闭；运行中的整合会话保留活动提示和停止/打开入口，未关联旧记录保留“整合空间（待关联）”恢复项。搜索与明确打开仍可达，孤儿不能被过滤后丢失。与删除整合 Session 或把它并入主聊天相比，呈现投影不会破坏独立修复上下文与成果保留。

### 4. 自动检查只在有限状态边界触发

准备完成事件、修复运行实际退出事件、面板重新可见，以及已知候选修订变化，触发当前可见操作的一次核对。控制器合并同身份/operation/候选版本的进行中检查；Verify 自身产生的新记录修订不得再触发 Verify。离线、失败或未知退出停止自动检查，提供手动重查；不做定时轮询。旧外部 Git 修改只能在返回/手动刷新时发现，不声称实时监听全部进程。

当前 Verify 只检查整合候选；扩展状态读取中的新鲜度投影可指出来源或目标已变，最终 Apply 的完整再次核对保持权威。检查结果按原修订安装，旧请求完成后不覆盖新候选。准备和最终应用仍分别展示冻结计划并由用户独立确认，不能把普通主按钮包装成隐式连续写入。

### 5. 有界结构化阻塞与验证来源

新增可选、版本化的显示投影，旧字符串字段保留：

- 阻塞包含 `side`（source/target/integration）、稳定原因、Session ID、根目录、相对路径/数量、活动引用、已知/未知及可用定位动作。Git 路径复用既有最多 500 项快照，不扩张文件访问；面板首屏最多 20 项，其余展开。缓冲区状态来自写入保护，不能由 Git 干净推断编辑器已保存。
- 目标文件动作进入正确 Session 的工程视图；活动入口指向真实运行，不自动停止、保存、提交、stash 或 reset。
- Git 结果直接绑定候选 OID；测试区只消费可核对的执行证据（候选 OID、命令/检查名、退出结果、时间、原日志引用）。已有记录缺少这些字段时显示“未验证，查看整合记录”，不解析任意聊天文字来伪造结构化通过。
- 本期不创建测试调度器。能够取得原执行结果时显示有界摘要和失败入口；只能取得原会话文本时提供证据链接并保持未知。候选变更使旧证据过期。可观察的失败在最终审阅中醒目保留；是否设置项目专属测试硬门槛沿用已有策略，不新增隐藏规则。

与自动运行整套测试或让模型总结决定通过相比，此方案避免未知命令权限、昂贵重复执行和乐观验收，同时让用户能找到真正的失败原因。

### 6. 持续并行开发

副本入口增加反向预览，来源是登记的主 Session，目标是当前副本，origin 仍为当前副本。复用 `projectMergePreview/Prepare/Verify/Apply` 和原 requestId/指纹/目标预留。服务端识别真实 task 父子方向为 `sync_main`；若冻结副本 HEAD 是主干 HEAD 的祖先，独立准备使用快进，避免多余 merge commit。若分叉则在独立空间保留双方历史并处理冲突。原合入与同步是两个操作，两份回执独立；同步失败不撤销已成功合入的主干，也不声称副本已更新。合入和同步的准备/应用都保持独立确认，不自动推进正在开发的其他副本。

`ProjectTasksPanel` 顶部增加“分支图”。`projectBranchGraph` 只读同 owner/executor 的主 Session 及最多 15 个普通副本，优先包含当前副本；整合分支不挤入普通分支图。使用真实 OID、父提交及 `rev-list` 领先/落后，按拓扑顺序从左到右绘制，下方列表联动已有提交详情和文件差异。默认最近 80 条，可显式扩大至 200 条，范围外父提交显示虚线；更多副本和不可读状态明确显示。读取期间 HEAD/分支变化则拒绝混合结果，旧节点/离线不显示为空仓库或自动换节点。没有轮询、fetch 或查看即写入。

多个副本可以并行开发，但应用到同一主干受现有目标预留保护。前一个合并推进主干后，后一个旧计划因指纹变化被拒绝，须重新预览并吸收已经合入的成果。Git 无文本冲突不等于功能兼容，继续保持项目测试证据独立展示。

## Risks / Trade-offs

- [两次独立确认仍需操作] → 精简其间的导航和人工核对，并明确两次确认各自影响；不承诺“一次点击自动完成全部写入”。
- [隐藏整合项可能降低发现性] → 活动/待处理徽标、原记录入口、已有标签和孤儿恢复项必须一起交付；关联缺失时保留可见。
- [来源/目标活动与外部 Git 修改存在竞态] → 服务端身份/指纹重查及目标写入保护始终保留；状态投影不作为执行授权。
- [自动 Verify 形成事件循环或串 Session] → 候选版本键、单次进行中合并、忽略自身检查修订、可见性门控及迟到结果测试。
- [旧记录没有可靠测试证据] → 明确未知和原日志入口，不伪造通过；旧验证结果不因新版 UI 升级可信度。
- [Windows 临时 Git 测试路径过长] → 测试使用独立短根，恢复 cwd 后清理，保留失败环境说明；不修改全局 Git/注册表来掩盖限制。
- [主聊天是目标活动] → 面板说明结束当前轮后才能应用；不以“只是写 proposal”为由豁免保护。

## Migration Plan

1. 先增加兼容的只读摘要、可选诊断与能力版本；旧客户端和已有记录保持可读，原写协议不变。
2. 接入连续面板、既有记录恢复及有界核对，验证所有权限/未知状态回归后，再切换整合项的默认呈现；回滚 UI 即恢复原树，不需要重建 Session 或 Git 目录。
3. 同步 `docs/session-collaboration-workflows.md`、`AGENTS.md` 与尚未归档的 `parallel-session-workspaces` 场景：保留父子归属，明确普通列表默认收拢整合空间。若实施时该 change 已归档，则按其真实主规格路径提交对应增量，不在两个位置写矛盾契约。
4. 以临时用户、短路径临时仓库、fake Backend 和隔离浏览器验证无冲突/冲突、旧记录、断线、目标活动与主题/窄屏；不把测试用合并当成用户项目合并授权。
5. 规划阶段的 proposal 保留在独立 detached worktree `awu-merge-proposal`，没有新增 Git 分支或 AWU Session。2026-11-08 实施前只读核对原合并操作 `86accbe7-8098-4660-9ea9-113180753a7d` 的成功回执和目标 `aa8423f2fb377c6e4116ca25cf63743c283ee039`，确认当前工作区无同名 change 后复制并逐文件核对。原规划 worktree 保留，实施发生在主工作区；没有再次执行用户项目合并、提交、安装或发布。
