# Kit 本机更新：本地直装与发布更新

在当前 Session 的 Workspace Kits 中选择所需路径。四条路径都保留独立安装确认与重启验收；点击运行不是静默安装授权。

| 路径 | 步骤 | 是否上传 |
| --- | --- | --- |
| 本机打包直接更新 | 构建 → 校验本地安装包 → 确认安装 → 重启验收 | 否 |
| 打包、发布并本地直装 | 构建 → 确认发布 → 校验同一份本地包 → 确认安装 → 重启验收 | 是，安装不重新下载 |
| 打包、发布并更新本机 | 构建 → 确认发布 → 下载本次发布 → 确认安装 → 重启验收 | 是 |
| 本机检查并更新 | 检查已配置更新源 → 下载 → 确认安装 → 重启验收 | 不构建、不上传 |

## 首次启用

先通过原有「节点在线更新」或安装包部署支持 Kit 更新协议的 Windows 桌面版本。仅更新网页或 Backend 不够；源码运行、旧桌面、Linux、Docker 和无法唯一确认的安装实例不支持这条新能力，原入口仍可使用。

发布制品必须包含 `kitUpdateProtocol: 1`。新的 `scripts/stamp_version.py` 会在后续正常构建时写入协议声明；修改源码不代表当前运行进程已升级，也不会自动重写旧制品的元数据。

## 生成与保存

### 打包、发布并本地直装

输入「本机打包发布后本地安装，不重新下载」。预览应包含构建引用、严格绑定的发布步骤和最后的本地安装步骤。保存不会执行，原有 Kit 不会自动改写。

1. 构建成功后确认发布同一次构建；上传、通道更新和保留清理规则仍使用发布中心的冻结计划。
   Windows 未指定制品类型时只发布 NSIS 的 `*-setup.exe`，MSI 留在本地。没有本次 NSIS 时提示缺少符合条件的制品，不自动改发 MSI；Linux/macOS 等其他平台沿用原筛选。明确填写类型或制品 ID 时按该范围发布。
2. 发布成功后，读取本机保存的实际上传清单，验证签名策略、版本、buildId、制品身份、大小与 SHA-256。只使用发布范围内的本次本地包，不再从远端下载安装包或读取 latest。
3. 多个兼容安装器需要选择；卡片显示「已发布 · 使用本地安装包」、真实发布通道和本地包路径。单独确认安装并重启后，继续核对实际版本。

发布失败就停止；本地包或发布清单缺失、被修改，或回执与本次构建不符也停止，不下载兜底。取消安装保留原本地包和已成功发布。要求清单签名的节点继续验证正式发布时产生的签名；不会用未签名构建回执代替。

此路线需要部署包含该扩展的应用版本，再在 Kit 编辑页按上述目标重新生成并保存。旧运行进程不会因工作区源码更新而自动具备该路线。

NSIS 默认选择规则在执行节点升级后对新发布计划生效；已保存且未指定类型的发布 Kit 无需重建。正在发布或已冻结的计划继续使用原制品快照，不会中途改变上传内容。

### 本机打包直接更新（不上传）

输入「本机打包直接更新，不用上传」。生成器复用当前 Session 已登记的构建 Kit，追加 `node.update_local_build`。保存后运行，构建成功便进入本地校验；**无需配置上传服务或更新源，也不下载安装包**。

1. 构建 Kit 使用支持登记的 `build_all.bat` 或 `register_release_candidate.py`，且仅包含执行端命令。候选不唯一时，生成器列出真实 ID 供选择。组合引用原 Kit，不改写它。
2. 只接收当前运行中唯一成功构建的回执。版本、项目目录、制品大小与 SHA-256 必须一致；不会扫描目录挑“最新包”，也不借用其他运行的制品。
3. 将安装包复制到节点更新暂存区，并复核大小和 SHA-256。存在多个兼容安装器时先选择；选择后不会更换构建。计划展示「本次本机构建 · 未上传」、原始安装包路径、执行设备与版本。
4. 在 Kit 面板点击「确认安装并重启目标节点」。后续退出、安装和验收复用现有更新流程。原构建目录中的安装包保留；交接前取消只释放本次更新占用。

这条路径不包含发布步骤，能力参数为空，不能传任意安装命令或路径。它仅支持已安装、具备更新协议的 Windows 桌面及匹配架构的 MSI/NSIS，目标必须比当前版本新。网络共享、越界路径和符号链接/重解析点不支持；源码运行、Linux/Docker 不支持此直装入口。

本地构建回执不等于签名发布清单。节点启用清单签名验证（要求签名或配置了验证密钥）时，此路径会明确拒绝；可使用上面的已签名发布后本地直装，或原发布下载流程。程序不会关闭签名策略。

### 只检查并更新本机（不构建、不发布）

输入「本机一键检查并更新」，生成器使用独立能力 `node.check_update_local`。它读取**执行设备更新中心已保存的清单地址与通道**；没有配置会明确提示，不推断发布地址、不借用其他运行的发布凭据。

- 检查成功后冻结清单、版本和摘要。多安装器须选择，选择与确认不会重新读取 latest 换装其他版本；下载仍核对大小与 SHA-256，签名验证沿用节点策略。
- 当前桌面、Backend 和清单完整版本一致时，结果为「检查完成，无需更新」，没有安装或重启回执。断网、旧清单、身份不明和签名失败不会被当成无需更新。
- 有更新仍必须在 Kit 面板单独确认安装；权限、忙闲、实例、预留、重启验收及未知结果保护与组合更新相同。不能由聊天发布委托批准安装。
- 旧的单步骤「本机一键检查并更新」如果错误使用 `node.update_local_published`，不会自动转换。升级应用后，在该 Kit 的编辑页按上述目标重新生成、检查预览并保存新版本；旧定义和历史记录不被后台改写。

Windows 安装目录识别兼容 NSIS 写入的带外层双引号的 `InstallLocation`，仍须真实目录匹配且没有多安装目录歧义。无需手动修改注册表。尚未包含此修复的桌面必须先通过原「节点在线更新」或安装包升级；修改工作区代码不会热更新正在运行的桌面壳。

### 构建、发布并安装本次版本

在当前 Session 的 Workspace Kits 中输入「打包上传，并完成本机更新」。

- 生成器从当前 Session 的真实、已启用 Kit 中查找使用 `build_all.bat` 或 `register_release_candidate.py` 的执行端构建步骤。
- 没有候选或有多个候选时，按返回的真实 ID 补充选择；自定义构建必须补齐可验证的登记输出，不能用“目录最新文件”替代。
- 预览包含构建引用、严格绑定发布和末尾的 `node.update_local_published`。保存不运行，也不改写原构建 Kit。
- 新能力不能放在中间或设置为定时任务；保存和运行都会检查展开后的顺序与循环依赖。
- `node.update_local_published` 前面必须有唯一的 `bindBuild` 发布步骤；缺少时拒绝保存/运行并指向独立检查更新入口，不隐式切换更新来源。

## 运行与两次确认

1. 运行组合。构建步骤通过独占请求登记本次版本、制品大小与 SHA-256；退出码为 0 但没有新制品仍会失败，后续步骤跳过。
2. 在发布计划中核对版本、平台、通道、上传地址、制品、保留清理规则与预检，然后单独确认发布。
3. 发布成功后，本地直装复制并校验同一次构建的本地包；原发布更新路线从该运行的不可变版本清单下载。即使 stable 已指向新版本，当前 Kit 也不会换装其他版本；签名要求保持节点设置不变。
4. 如果有多个兼容安装器，先选择。安装计划显示执行设备、安装实例、当前与目标完整 buildId／sequence、通道、大小、SHA-256、计划指纹和退出影响。
5. 结束执行设备上的其他工作，再点击「确认安装并重启目标节点」。确认时重新检查权限、实例和忙闲状态；有聊天、LOOP、序列派发、其他 Kit、受管任务或未知退出时拒绝交接，不会后台等到空闲后突然安装。

“本机”固定为 **Session 所属执行设备**。远端控制窗口不会安装或退出；通知只交给绑定的本地桌面。普通更新中心和此 Kit 共用节点预留，不能互相覆盖。

聊天的 `Kit 代确认` 只沿用原有发布委托范围，不能确认安装、重启或扩张混合链路授权。聊天查询会返回完整安装计划、`canApprove=false` 及面板指引。

## 何时算成功

启动助手、安装器退出码为 0、客户端断线或返回 `waiting_restart` 都不代表成功。需要同时核对本请求的安装回执、相同设备／安装实例、桌面与 Backend 的完整发布身份，以及在线本地连接，才将**原 Kit 运行**标为成功。

更新助手对每个请求仅领取一次，不按进程名结束程序；新版交接仅关闭当前桌面持有的 sidecar，不使用全局 PID 文件猜测其他实例。安装失败和重启启动失败分别保留，已成功发布的版本不会被撤销。

## 取消与恢复

- 准备、复制/下载和待安装确认时可以取消，只释放本请求的暂存占用；不删除原本地构建或已发布制品。
- 确认交接后不能保证撤回。关闭 Kit 面板或聊天不会停止安装，不提供强杀安装器、自动回滚或重装。
- 重新连接时自动核对原请求；最多 13 次、间隔 15 秒，验收超过 180 秒仍未确认则显示结果未知，停止自动检查。
- 结果未知时点「只读核对原安装结果」，查看安装回执与实际版本。`kitResume` 对这种运行也只核对，不重新构建、发布或安装。
- 手动安装后重新启动，若同一安装实例的桌面与 Backend 完整版本一致且达到原目标，原请求从未领取或启动助手，系统会原子封闭旧请求的启动入口，保留原 Kit 失败记录并恢复节点操作。没有安装回执时不会把旧 Kit 标为成功；已有助手启动标记、损坏回执或版本/实例不一致仍保留保护。历史 Kit 记录缺失也不妨碍清除已结束请求自身的内存屏障。
- 回执损坏、无法证明助手退出或记录写入不确定时保留节点保护。不要删除 journal、修改回执或重新运行来绕过；先检查目标设备实际安装和进程状态，必要时按明确的人工恢复方案处理。
- 同一确认重试复用原 requestId；账号／设备切换后不把旧响应显示到新目标，不回退默认节点。未获得确认结果时先查询，不自动重发写操作。

旧版若报「活动记录超过安全核对范围或存在重定向」，其中一个原因是把超过 16 MiB 的 LOOP 历史正文按活动状态处理。修复版分块校验原文件，只提取安装忙闲所需状态，不删除或迁移历史；真实未结束活动、损坏、重定向及核对期间变更仍会阻止安装。检查保留 512 份文件、单次读取 64 MiB 和活动投影 16 MiB 的上限，超限分别说明原因。

选择安装器后，等待复制/下载的提示只保留到暂存结束；失败或进入独立确认后不再显示旧进度，迟到的选择回执也不能覆盖结果。选择阶段已经展示当前版本。此修复须部署到执行设备的应用中才能生效，工作区源码变化不会修改旧进程或重放失败运行。

## 验证范围

本变更使用临时用户根、假发布服务、假安装器和隔离浏览器验证协议与界面。没有发布真实制品、运行真实 MSI／NSIS、退出当前应用或完成生产安装验收。Windows 安装注册信息、权限策略及签名制品的实际升级仍需在单独授权的测试安装上验证。

详见 [验证记录](kit-local-update-verification.md) 和 [原节点更新入口](node-updates.md)。
