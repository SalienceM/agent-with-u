# LOOP 自适应交付与停滞诊断

## 解决的问题

旧默认策略把每轮限制为“唯一最小焦点”，上轮评审又不断把局部缺口传回规划。
对已有 OpenSpec 任务表的实现工作，这容易形成审计、补证据、再次审计的串行队列，
即使还有大量独立实现任务可以推进。独立模型上下文也不能继承普通对话中全部工作流决策，
更不等于文件或用户数据隔离。

## 新行为

- **工作流交接**：普通 Session 转为 LOOP 时保留最近 12 条可见消息的有界、脱敏摘录及绑定 Skill ID。
  旧 LOOP 在下一次 prepare 补建交接。当前 Session 约束和 Skill 提示随调用传入；历史文本只是定位线索，
  不是新指令、完成证据或旧授权的复用。不会复制附件、隐藏思考、工具结果或整份历史。
- **按依赖选择批次**：策略支持自动识别、任务交付、探索验证。交付模式以真实任务来源和稳定编号为准，
  每轮仍最多编排 4 步，但一步可以完成多个相关就绪任务，不固定为审计→实现→复核→文档。
  探索模式可以推进可验证的假设，不强迫所有工作套用 OpenSpec。
- **阻塞有范围**：评审台账区分局部、全局、安全和人工输入阻塞，并记录影响任务及解除条件。
  局部阻塞不自动阻止独立任务；安全事故未遏制或全局阻塞则暂停 Auto。历史数据无法恢复的损失
  与仍在持续的风险分开记录，不能静默豁免，也不能无限重复相同恢复尝试。
- **证据复用**：顺序步骤沿用本轮上下文，新上下文、并发后的步骤和重试补传已有步骤证据。
  分析获得有界原始输出首尾，保留末尾失败信息；移除额外的模型汇总调用。
  历史证据只有版本、环境和影响范围仍适用才能复用，否则定向复查。
- **识别空转**：依据稳定任务状态和整体 verify 状态与证据比较推进，不把分数上涨、改写描述或工具活动当作进展。
  无推进时要求换路规划，并重新检查方向；默认连续 3 次无推进暂停 Auto，可设置为 2–8 次。
  暂停原因、可继续任务和范围丢失警告在面板及流程视图显示。用户补充条件后可显式再次运行。
- **收口验收**：分数不能单独宣告完成。新记录还需完整稳定范围、任务已验证或明确人工依据、
  整体 verify 通过且有证据、无剩余阻塞和未处理 Addon。任务台账按需加载，可展开查看依赖与证据。
  风险/预算导致的退出仍不是成功交付。

## 安全与限制

自动 Codex 迭代为规划和只读步骤请求原生 `read-only`，写步骤与分析请求 `workspace-write`；
不支持时按失败处理，不自动降级为全权限。普通聊天权限不受此项修改影响。
这项实现有协议回归测试，但实际操作系统隔离依赖安装的 Codex 版本与平台能力；
其他 Backend 目前只获得相同的执行约束，不应宣称具备相同的原生隔离。

每次调用的角色说明与实际请求访问模式使用同一来源。规划阶段只读不代表整个 Session 无写权限：
规划器可以安排已获授权的 write/sequential 步骤，由执行器后续单独请求工作区写入；
不能仅凭规划阶段只读或一次真实用户文件读取失败而全局暂停，也不能因此绕过实际拒绝。
旧记录中的“下一唯一焦点”应结合更新的明确用户处置范围重新判断，而不是永久锁定队头。
历史损失不会自动被清除、豁免或视作已恢复，真实持续风险及必要授权仍保留暂停门槛。

可能写入用户数据的测试必须使用独立测试用户目录并核实实际写入位置。
项目 Git 快照不能保护工作区之外的真实用户目录。模型返回明确 `loopControl.pause` 时，
系统在模型调用返回后停止后续步骤/阶段；这不是调用执行中的即时写操作拦截器。
已经并发启动的调用不因另一调用返回暂停信号而自动撤销。

Backend 在部分文本后报错不会被记为成功；失败后的潜在依赖步骤停止盲目执行并进入评审。
自动收口或评分下降不再触发恢复所谓“最佳”Git 快照，避免覆盖后续成果；
用户显式丢弃/恢复的独立流程保留。

台账来自模型评审和引用的证据，不是系统自动验证的哈希证明。
长任务若始终没有可记录的状态推进也会触发保守暂停，应在真实任务边界拆分或调整耐心值，
不能通过虚假勾选来规避。报告上限为 100 项任务、50 项阻塞；超过或未完整清点不能自动收口。

## 兼容与生效

- 旧记录不被倒推为“已停滞”；新报告的首次有效清点建立比较基线。
- 已知旧默认策略迁移到批次策略；用户自定义策略和默认策略之后追加的要求保留。
- 旧客户端保存策略时不抹掉新增模式和耐心值；进度暂停随 LOOP 状态持久化。
- 更新并重启 AWU 后端后，新 prepare 开始使用上述逻辑。修改代码本身不会改变已运行进程。
- 本次实现不重启服务、不干预正在执行的其他 Session，也不恢复历史已损坏数据。

## 回归入口

后端：`tests.test_loop_delivery`，以及 evolution/core/stage_details/diagnostics/session_to_loop/
lifecycle/codex_office/codex_remote/skill_library_responsiveness 相邻测试。

前端：`frontend/tests/acceptance/loop-stage-details.spec.ts` 的桌面与移动端验收，
包括暂停提示、阻塞范围、人工依据及展开详情不增加轮询；另运行 TypeScript 检查和生产构建。
所有测试使用隔离夹具或模拟 Backend，不调用真实模型、不操作用户项目数据。

## 调用结束后的决定

LOOP 分别保存调用结果、任务验收和调度决定。`normal` 只表示一次 Backend 调用正常结束；
非空总结、一次测试或一次提交都不代表完整目标已经验收。步骤的验收无法可靠映射时显示“尚未核实”，
累计台账可显示部分成果。阶段、恢复和轮次边界的决定及引用保存在详情中，紧凑推送只传最新摘要。

决定依次服从用户停止/控制权、旧调用退出确认、安全/授权/全局阻塞、绑定来源核对、完整验收，
再考虑预算/风险/真实连续失败、Auto 和无进展。完整验收恰在预算最后一次满足仍可如实完成；
预算耗尽而验收不足只显示停止和未完成。独立评审开启时仍需至少两次有效评审及原有收敛门槛。
明确人工项保留正式分母和原文依据，显示“自动范围完成，待人工核验”。

等待用户、无进展、来源不可核对采用 `terminalKind=paused`，不写成 Backend 错误。
明确恢复后从新的 prepare 复核已有成果；真正中断的未终结记录仍按原断点恢复。
旧调用退出未确认时禁止新增写调用。重复结束事件按决定身份和原任务注册表去重；打开面板、
重连或重启不会重放历史继续决定。取消不承诺撤销工具已经产生的副作用。

## 显式绑定 OpenSpec 来源

在 LOOP 的“任务来源”卡点击“发现 OpenSpec 来源”，选择 change，再点击“确认绑定”。
即使只有一个候选也要确认。发现、绑定、重新核对、查看详情均不会启动 Auto 或执行下一轮。
运行中、人工接管中及有可恢复记录时不能改绑；先处理该记录。普通聊天和普通 apply 不调用此适配器。

- 仅支持该 Session 执行节点的工作区内项目。经 Relay 访问执行节点可用；SSH 文件系统、父项目、
  外部/声明式 store、越界符号链接不支持。不回退别的节点或 Backend，也不安装 CLI 或初始化项目。
- CLI 优先使用工作区 `node_modules/.bin`，其次是实际 execute Backend 的 PATH。
  工作区、Backend 环境或 CLI 版本变化需重新发现并确认；不会借用规划/评审 Backend 的 CLI。
  “重新核对来源”和“确认范围修订”不能静默改绑；检测到变化时保留旧绑定、快照及未解决问题。
  显式来源操作重新查询 CLI 版本，不复用失败操作的旧版本缓存；同边界的在途查询仍合并。
- 只执行固定的版本、list、status、instructions apply 查询，不执行任务正文或返回指令。
  Windows 使用受限的 `.cmd` 包装；可执行文件路径中不支持的 shell 元字符会明确拒绝，cwd 不经 shell 拼接。
- 单进程查询超时 20 秒、快照流程 60 秒，最多一次瞬态重试；超时后关闭并确认进程退出。
  stdout/stderr 和规范化快照各最多 1 MiB，正式任务最多 100 项。超限或协议不支持是不可核对，不是零剩余。
- 绑定、prepare 前、execute 后、恢复时取只读快照；写调用/收口前检查文件依据是否变化。
  相同边界合并并仅复用仍有效的快照，无计时器扫描或流式轮询。不是文件锁，无法排除外部并发修改。

1.13.1 的 CLI `tasks.id` 是位置序号。本适配器逐项核对 `contextFiles.tasks` 中的真实 checkbox，
提取显式编号（例如 `1.1`），记录实际路径和行号；忽略围栏内的示例任务。支持逐项 sourcePath/line
的协议也要核对真实文件。无稳定编号、重复编号、多文件歧义和清单不一致均明确失败。
勾选、空白、任务位置变化更新状态，不创造新范围或新进展；描述、验收依据、增删和重编号变化显示范围差异。

范围冲突时在空闲状态填写处置依据并“确认范围修订”；确认期间又有变化则重新核对。
改绑或解除绑定同样要记录旧范围处置，历史和未解决问题保留在来源详情。
查询失败保留旧快照并标不可核对，CLI `blocked` 单独显示工作流阻塞；二者都不能用于自动写入或成功收口。
适配器绝不自动勾选 tasks.md。全部勾选仍须经过真实证据、整体验证、Addon 和评审门槛。
正式清单未勾完不妨碍有效子项记录增量；但评审模式不符、来源不匹配或正式任务映射有遗漏时，
该报告不能显示累计验收已通过，也不能刷新进展或消耗子项高水位，需重新核对。

## 子里程碑与正式分母

prepare 可登记可独立验收的子条件，关联稳定父任务和原条件原文；执行前冻结，评审核对映射及证据。
每个父任务最多 20 个、范围内累计最多 200 个子项。漏报旧子项不会抹掉已登记条件；超限明确不完整。
规划重试耗尽后的只读诊断也继承历史范围，包括已登记但尚无有效评审的子项；遗漏不能绕过验收。
范围登记与成果基线分别继承：无效整体报告不提供已验证状态或证据，也不消耗后续有效推进的信用。
登记已经存在的成果只建立基线；执行后新发现的子项保留为待核对基线候选，不算本轮新增。

正式任务仍可为 **2/25**，同时显示“外壳子项已实现待验/已验证”。首次有证据的实现或验证推进
可重置无进展计数，但子项不进入 25 的分母、不自动勾选父任务，也不替代父任务的集成验收。
相同父任务/原验收条件按高水位去重，换名、重复测试、重复证据和恢复旧高水位不重复计信用。
只有经过映射核对的交付条件计入，不按文件、命令、提交或字数计量；自然语言等价仍依赖评审判断。

证据记录工作区相对路径、内容 SHA256、实际验证命令/结果和环境指纹。这里只读核对身份，
不会运行证据里写的命令，不访问工作区外用户目录。相关文件变化、缺失或环境变化会使对应子项待复验；
无关文件或 Git HEAD 变化不会要求全量重验。历史高水位保留，不能覆盖当前回归或支持错误收口。
这些仍是有边界的评审观察，不是内容正确性的机器证明。

## 新协议兼容与回退

结果协议为 outcomeVersion 1，子项进展协议为 progressVersion 2。旧字段保持兼容投影；
旧记录缺失信息维持未知，不猜暂停原因、不构造历史子项，也不自动绑定来源。
旧客户端只更新策略不会清空来源、范围修订或里程碑；既有自定义策略、预算和历史损失保持。
新入口默认未绑定，通用 LOOP 无 CLI 依赖。

这次修改只完成代码和隔离测试，未更新运行中的生产进程。由用户另行安排更新/重启。
回退前先暂停相关 Auto 并备份 stage 文件；旧版本不具备新来源/子项验收门槛，不能静默降级续跑。
保留新增字段和历史；不要以清理状态方式解除等待。

验收命令、隔离范围和逐场景测试映射见
[`improve-loop-continuation-and-progress` 验收记录](../openspec/changes/improve-loop-continuation-and-progress/verification.md)。
